# セキュリティチェックリスト

## OWASP Top 10 観点

| # | カテゴリ | このリポジトリでの確認観点 |
|---|---------|-------------------------|
| A01 | アクセス制御の不備 | `gh` / `git` 操作の認証・権限スコープが適切か |
| A02 | 暗号化の失敗 | トークン・パスワードが平文でログ出力・コミットされていないか |
| A03 | インジェクション | シェルコマンドへの外部入力が適切にクォート・エスケープされているか |
| A04 | 安全でない設計 | 最小権限原則に従っているか（Agent の tools リスト等） |
| A05 | セキュリティの設定ミス | デフォルト認証情報・デバッグ出力の残留がないか |
| A06 | 脆弱な既知のコンポーネント | 外部スクリプトの無検証実行がないか |
| A07 | 認証・セッション管理の不備 | `gh auth` の状態確認・トークン有効期限の考慮があるか |
| A08 | データとソフトウェアの整合性 | スクリプト・設定ファイルの改ざん検知の考慮があるか |
| A09 | セキュリティログの不備 | エラー・失敗が適切にレポートされるか |
| A10 | SSRF | `WebFetch` 使用時のドメイン制限・外部 URL の検証があるか |

## ハードコード秘密情報

チェック対象:

- `.env`・`.env.local`・`*.env` ファイルのコミット混入
- `GITHUB_TOKEN`・`GH_TOKEN`・API キーの直書き
- パスワード・秘密鍵の変数への代入（`password=`・`secret=`・`token=` 等）
- 認証情報を埋め込んだ接続文字列（`scheme://user:pass@host`）・JWT
- 構造化ファイル（`config.yml`・`settings.json`・`*.tf`・k8s manifest 等）に直接書かれた実値

検出コマンド例（`create-commit` Step 2 と同じ正規表現。ERE で書く）:

```bash
# 追加行のみを対象にする。`grep -v '^\+\+\+'` は BRE で `\+` が量指定子と解釈される
# 実装（GNU grep / ugrep）で構文エラーになり、`|| echo "検出なし"` と組むと fail-open に
# なるため、必ず `-E` を付けて `grep -vE '^\+\+\+'` と書く。
# 鍵名は `[a-z_]*token` のように接頭辞を問わない形にする。`access_?token` 等を個別に
# 列挙すると `GITHUB_TOKEN` / `GH_TOKEN`（上のチェック対象に明記した名前）を取りこぼす
git diff --staged --diff-filter=ACMR | grep -E '^\+' | grep -vE '^\+\+\+' \
  | grep -iE '(password|passwd|secret|client_secret|api_?key|[a-z_]*token|aws_secret_access_key|private_?key)[[:space:]]*[:=][[:space:]]*[^[:space:]]{8,}'

git status --short | grep -E '\.env'
```

除外パターン（`grep -vE` によるプレースホルダ・環境変数参照の除去）も同じ経路で fail-open する。
除外側が構文エラーになると、検出済みの行が消えたうえで非ゼロ終了し「検出なし」になる。
**検出側・除外側の双方を既知サンプルで自己テストしてから本検査を走らせる**（実装は
`skills/create-commit/SKILL.md` Step 2 (a)。パターンは変数へ一度だけ定義し、自己テストと
本検査で同じ文字列を共有する）。

**パターン照合は網羅的な検出ではない。** 任意の変数名に代入された認証情報、値の形式に規則性が
無い自社発行トークン、除外パターンに偶然一致する実値は原理的に拾えない。したがって
**パターンが何も検出しなかった場合でも、staged 差分の追加行を秘密情報の観点で目視レビューする**
（手順の詳細は `skills/create-commit/SKILL.md` の Step 2 (b)）。

GitHub の secret scanning / push protection を有効化している場合、それは push 時点の**追加の**
防御線であり、この手順の代替にはならない（ローカルコミット時点では働かない）。

発見した場合は**コミット・PR 作成を中止**し、ユーザーに警告する。

## コマンドインジェクション

`gh`・`git`・シェルコマンドへ外部入力を渡す場合:

- 変数は `"${var}"` でクォートする
- ユーザー入力をそのままコマンドに展開しない
- HEREDOC（`<<'EOF'`）でシングルクォートをエスケープなしに使用する

悪い例:
```bash
git commit -m $user_input                # 未クォート展開。単語分割・グロブ展開が起き、オプション注入が可能
bash -c "git commit -m '$user_input'"    # コマンド文字列の組み立て。シングルクォートを閉じる入力で任意コマンドを注入可能
```

なお、クォート済み展開（`git commit -m "$user_input"`）は単一引数として渡されシェルで再評価されないためコマンドインジェクションにはならないが、信頼できない内容をそのまま受け入れないための妥当性検証は別論点として必要になる。

良い例:
```bash
git commit -m "$(cat <<'EOF'
feat: ユーザー提供のタイトル
EOF
)"
```

## SSRF（Server-Side Request Forgery）

`WebFetch` ツールを使用する場合:

- 許可ドメインを明示する（例: `github.com`・`docs.github.com`）
- ユーザー入力の URL をそのまま `WebFetch` に渡さない
- プライベート IP アドレス（`localhost`・`127.x`・`10.x`・`192.168.x`）へのアクセスを禁止

## フック回避禁止

```bash
git commit --no-verify   # 禁止
git push --no-verify     # 禁止
```

pre-commit フックはセキュリティ・品質ゲートの役割を担うため、**いかなる理由があっても迂回しない**。フックが失敗した場合は原因を調査・修正してから再実行する（詳細は `./conventional-commits.md`）。

## 問題発見時のアクション

| 重大度 | アクション |
|--------|-----------|
| 高（秘密情報露出・インジェクション） | 処理を即座に中止。ユーザーに警告して修正を要求 |
| 中（設定ミス・権限過剰） | ユーザーに警告。修正確認後に再試行 |
| 低（ログ不足・改善提案） | レポートに記載して続行 |

セキュリティ問題が**未解決**の場合、PR 作成・マージをブロックする。
