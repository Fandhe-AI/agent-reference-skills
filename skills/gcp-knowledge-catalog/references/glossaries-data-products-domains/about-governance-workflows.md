# About governance workflows

Governance workflows in Knowledge Catalog (formerly Dataplex Universal Catalog) add automated controls and approval mechanisms for requesting access to data products and for curating catalog and glossary metadata. This feature is in Preview ("Pre-GA Offerings Terms"); requesting single metadata changes to business glossaries and entries is in private preview and needs an access form.

## Signature / Usage

Snippet borrowed from the request-management page (the overview itself shows no code). Lists requests pending review in one project and location:

```bash
curl -X GET \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://dataplex.googleapis.com/v1/projects/PROJECT_ID/locations/LOCATION/changeRequests?filter=state=NEW"
```

### Use cases

- Data product access management: a consumer requests access to a curated data product; on approval the IAM roles are provisioned automatically.
- Business glossary curation: contributors or contractors submit requests that central data stewards review before the glossary is updated.
- Catalog entry and batch metadata enrichment: contributors or enrichment agents propose single or batch updates (custom entries, descriptions, aspects, links to glossary terms) for owners to approve in one workflow.

### Batch requests

Batch metadata change requests group operations through the Dataplex API. They originate either from a user's REST request or from an enrichment agent run whose recommendations need human review instead of auto-publishing.

## Options / Props

### Supported metadata operations (single requests)

| Resource | Create | Update | Delete |
|----------|--------|--------|--------|
| Glossary category | Yes | Yes | Yes |
| Glossary term | Yes | Yes | Yes |
| Entry | Yes | Yes | Yes |
| Entry link | Yes | No | Yes |

### Supported batch metadata operations

| Resource | Create | Update | Delete |
|----------|--------|--------|--------|
| Entry | Yes | Yes | Yes |
| Entry link | Yes | Yes | Yes |

### Request statuses

| Status | Single requests | Batch metadata change requests |
|--------|-----------------|--------------------------------|
| `NEW` | Pending review. Only the author can edit; only the author or a workflow administrator can delete | Pending review. The author can edit user-submitted requests, reviewers can edit enrichment agent requests, and the author or a workflow administrator can delete |
| `APPLYING` | Not applicable | Approved and being applied in the background |
| `APPROVED` | Approved and applied | Approved, and at least one change in the batch succeeded; item-level errors are listed in the response |
| `FAILED` | Could not be applied; updating the request resets it to `NEW` for re-approval | None of the changes could be applied; updating the request resets it to `NEW` for re-approval |
| `REJECTED` | Declined by an approver; no changes applied | Declined by an approver; no changes applied |

### Roles

| Role | Description |
|------|-------------|
| Requester | Creates and submits requests; can edit or delete their own requests while in `NEW` |
| Approver | Reviews, approves or rejects requests; for batch requests generated by the enrichment agent, can also edit the proposed changes before approving |
| Workflow administrator | Monitors compliance, configures workflow policies, maintains the backlog; views audit trails across all states and can delete requests in any state |

### Limitations

| Limitation |
|------------|
| Not supported for Assured Workloads projects |
| Does not support customer-managed encryption keys (CMEK) |
| Does not support VPC Service Controls |

## Notes

- Source: https://docs.cloud.google.com/knowledge-catalog/docs/about-governance-workflows (retrieved 2026-11-19; CC BY 4.0, code samples Apache 2.0)
- Snippet taken from https://docs.cloud.google.com/knowledge-catalog/docs/manage-requests
- Concurrency: several pending metadata change requests can coexist on one resource. Knowledge Catalog uses a last-writer-wins model: the most recently approved change overwrites earlier updates regardless of submission order, and pending requests stay valid even if the resource is updated directly or by another approved request.
- A request that is manually deleted, whose target resource is deleted, or that expires after 90 days is permanently removed; later queries return `404 NOT_FOUND`.
