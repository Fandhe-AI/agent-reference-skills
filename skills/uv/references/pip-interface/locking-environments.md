# Locking environments

Locking is to take a dependency, e.g., `ruff`, and write an exact version to use to a file, so the environment can be reproduced. uv allows dependencies to be locked in the `requirements.txt` format.

## Signature / Usage

```console
$ uv pip compile pyproject.toml -o requirements.txt
```

By default the `uv pip compile` output is just displayed; `--output-file` / `-o` is needed to write to a file.

## Locking requirements

```console
$ uv pip compile requirements.in -o requirements.txt                 # requirements.in
$ uv pip compile pyproject.toml requirements-dev.in -o requirements-dev.txt   # multiple files
$ uv pip compile setup.py -o requirements.txt                        # legacy setup.py / setup.cfg
$ echo "ruff" | uv pip compile -                                     # stdin
$ uv pip compile pyproject.toml --extra foo                          # one extra
$ uv pip compile pyproject.toml --all-extras                         # all extras
$ uv pip compile --group foo                                         # dependency group
$ uv pip compile --project some/path/ --group foo --group bar
$ uv pip compile --group some/path/pyproject.toml:foo --group other/pyproject.toml:bar
```

Extras are not supported with the `requirements.in` format.

## Upgrading requirements

When using an output file, uv considers the versions pinned in an existing output file. If a dependency is pinned it will not be upgraded on a subsequent compile run.

```console
$ echo "ruff==0.3.0" > requirements.txt
$ echo "ruff" | uv pip compile - -o requirements.txt
# This file was autogenerated by uv via the following command:
#    uv pip compile - -o requirements.txt
ruff==0.3.0
```

To upgrade a dependency, use `--upgrade-package`:

```console
$ echo "ruff" | uv pip compile - -o requirements.txt --upgrade-package ruff
```

To upgrade all dependencies, there is an `--upgrade` flag.

## Syncing an environment

Dependencies can be installed directly from their definition files or from compiled `requirements.txt` files with `uv pip install`. When installing with `uv pip install`, packages that are already installed will not be removed unless they conflict with the lockfile, so the environment can have dependencies that aren't declared in the lockfile. To ensure the environment exactly matches the lockfile, use `uv pip sync`.

```console
$ uv pip sync requirements.txt
$ uv pip sync pylock.toml          # PEP 751 pylock.toml
```

## Adding constraints

Constraints files are `requirements.txt`-like files that only control the version of a requirement that's installed. Including a package in a constraints file will not trigger the installation of that package. Constraints can be used to add bounds to dependencies that are not dependencies of the current project.

```requirements
pydantic<2.0
```

```console
$ uv pip compile requirements.in --constraint constraints.txt
```

Multiple constraints can be defined in each file and multiple files can be used. uv also reads `constraint-dependencies` from the `pyproject.toml` at the workspace root, and appends them to those specified in the constraints file.

## Adding build constraints

Similar to constraints, but specifically for build-time dependencies, including those required when building runtime dependencies. Including a package in a build constraints file will not trigger its installation at build time; constraints apply only when the package is required as a direct or transitive build-time dependency.

Given a package that defines:

```toml
[build-system]
requires = ["setuptools"]
build-backend = "setuptools.build_meta"
```

a build constraints file can pin `setuptools` for every package in the workspace:

```requirements
setuptools==75.0.0
```

uv also reads `build-constraint-dependencies` from the `pyproject.toml` at the workspace root. To require hashes for build dependencies, add them to the build constraints file and pass `--require-build-hashes`:

```requirements
setuptools==83.0.0 --hash=sha256:29b23c360f22f414dc7336bb39178cc7bcbf6021ed2733cde173f09dba19abb3
```

```console
$ uv pip compile requirements.in --build-constraint build-constraints.txt --require-build-hashes
```

This option only applies to build dependencies. To check runtime dependencies with `uv pip install` or `uv pip sync`, use `--require-hashes`.

## Overriding dependency versions

Overrides files are `requirements.txt`-like files that force a specific version of a requirement to be installed, regardless of the requirements declared by any constituent package, and regardless of whether this would be considered an invalid resolution. While constraints are additive, overrides are absolute: they completely replace the requirements of the constituent packages. Overrides are most often used to remove upper bounds from a transitive dependency (e.g., `a` requires `c>=1.0,<2.0` and `b` requires `c>=2.0`).

```requirements
c>=2.0
```

```console
$ uv pip compile requirements.in --override overrides.txt
```

Resolution can then succeed, but if `a` is correct that it does not support `c>=2.0`, a runtime error will likely be encountered. Multiple overrides can be defined in each file and multiple files can be used.

## Notes

- The official docs omit the `echo "ruff" |` input in the `--upgrade-package` example; it is added here because `-` reads requirements from stdin.
- `--group` is an addition not present in pip-tools' `pip compile` (they are considering it); uv expects to support whatever syntax and semantics they adopt. `--group` flags do not apply to other specified sources: `uv pip compile some/path/pyproject.toml --group foo` sources `foo` from `./pyproject.toml`, not `some/path/pyproject.toml`.
- Changed in 0.13.0: `--require-hashes` in constraints files included with `-c` from a requirements file is now honored (previously ignored); hashes are required for all requirements in the installation, and there is no opt-out while the directive is present. Add the missing hashes, or remove the `--require-hashes` directive from the included constraints file. See `../getting-started/breaking-changes-0-13.md`.
