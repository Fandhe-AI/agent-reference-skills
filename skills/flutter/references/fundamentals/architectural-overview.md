# Flutter architectural overview

A high-level overview of the architecture of Flutter, including the core principles and concepts that form its design. For how to architect a Flutter app, see the app architecture guide.

Flutter is a cross-platform UI toolkit designed to allow code reuse across operating systems such as iOS, Android, web, and desktop, while allowing applications to interface directly with underlying platform services. During development, Flutter apps run in a VM that offers stateful hot reload without a full recompile. For release, apps are compiled directly to machine code (Intel x64 or ARM instructions), or to JavaScript if targeting the web. The framework is open source under a permissive BSD license.

## Signature / Usage

`UI = f(state)`: a widget declares its user interface by overriding `build()`, which converts state to UI. The root widget is typically `MaterialApp` or `CupertinoApp`.

```dart
import 'package:flutter/services.dart';
import 'package:material_ui/material_ui.dart';

void main() => runApp(const MyApp());

class MyApp extends StatelessWidget {
  const MyApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      home: Scaffold(
        appBar: AppBar(title: const Text('My Home Page')),
        body: Center(
          child: Builder(
            builder: (context) {
              return Column(
                children: [
                  const Text('Hello World'),
                  const SizedBox(height: 20),
                  ElevatedButton(
                    onPressed: () {
                      print('Click!');
                    },
                    child: const Text('A button'),
                  ),
                ],
              );
            },
          ),
        ),
      ),
    );
  }
}
```

### Architectural layers

Flutter is an extensible, layered system: a series of independent libraries that each depend on the underlying layer. No layer has privileged access to the layer below, and every part of the framework level is designed to be optional and replaceable.

- **Embedder (platform-specific):** provides an entrypoint; coordinates with the OS for rendering surfaces, accessibility, and input; manages the message event loop. Written in Java and C++ for Android, Swift and Objective-C/Objective-C++ for iOS and macOS, and C++ for Windows and Linux. Flutter code can be integrated into an existing app as a module, or be the entire app.
- **Flutter engine:** mostly C++; rasterizes composited scenes whenever a new frame needs to be painted. Provides the low-level implementation of Flutter's core API: graphics, text layout, file and network I/O, a Dart runtime, and compile toolchain. It is exposed to the framework through `dart:ui`, which wraps the C++ code in Dart classes (lowest-level primitives for input, graphics, and text rendering).
- **Flutter framework (Dart)**, bottom to top:
  - Foundation classes and building-block services: `foundation`, `animation`, `painting`, `gestures`.
  - The **rendering layer**: an abstraction for layout; a tree of renderable objects that updates layout automatically.
  - The **widgets layer** (core SDK): a composition abstraction. Each render object has a corresponding class in the widgets layer, and you can define reusable combinations. The reactive programming model is introduced here.
  - The **Material** (`material_ui`) and **Cupertino** (`cupertino_ui`) packages: comprehensive sets of controls implementing the Material or iOS design languages using the widget layer's composition primitives.

The framework is relatively small; many higher-level features are packages (platform plugins like `camera` and `webview_flutter`, and platform-agnostic features like `characters`, `http`, and `animations`). The Material and Cupertino UI packages are on pub.dev, so you can import them or build your own design system on the core `widgets` library without bloating your app.

### Anatomy of an app

A regular app generated by `flutter create`:

- **Dart App**: composes widgets into the desired UI; implements business logic; owned by the app developer.
- **Framework** (`packages/flutter/lib`): higher-level API to build high-quality apps (style-neutral widgets, hit-testing, gesture detection, accessibility, text input); composites the app's widget tree into a scene.
- **Engine** (`engine/src/flutter/shell/common`): rasterizes composited scenes; low-level implementation of core APIs (graphics, text layout, Dart runtime); exposes functionality to the framework via the **dart:ui API**; integrates with a platform via the Engine's **Embedder API**.
- **Embedder** (`engine/src/flutter/shell/platform`): coordinates with the OS for rendering surfaces, accessibility, and input; manages the event loop; exposes **platform-specific API** to integrate the embedder into apps.
- **Runner**: composes the pieces exposed by the embedder's platform-specific API into an app package runnable on the target platform; part of the app template generated by `flutter create`, owned by the app developer.

### Reactive user interfaces

Flutter is a reactive, declarative UI framework: the developer provides a mapping from application state to interface state, and the framework updates the interface at runtime when state changes. In most traditional frameworks the initial state is described once and then separately updated by user code in response to events, which makes state changes cascade through the whole UI as it grows. MVC pushes data changes through the controller, but creating and updating UI elements are then two separate steps that can get out of sync.

Flutter explicitly decouples the user interface from its underlying state. With React-style APIs you only create the UI description, and the framework uses that one configuration to both create and update the UI. Widgets (akin to components in React) are immutable classes used to configure a tree of objects; these manage a separate tree of objects for layout, which manages a separate tree for compositing. Flutter is, at its core, a series of mechanisms for efficiently walking the modified parts of trees, converting trees of objects into lower-level trees, and propagating changes across them.

The `build()` method is by design fast to execute and should be free of side effects, so the framework can call it whenever needed (potentially once per rendered frame). This relies on fast object instantiation and deletion, for which Dart is well suited.

### Widgets

Widgets are the unit of composition: each widget is an immutable declaration of part of the user interface, forming a hierarchy by composition up to the root widget. Apps update their UI in response to events by telling the framework to replace a widget in the hierarchy with another; the framework compares new and old widgets and efficiently updates the UI.

Flutter has its own implementation of each UI control rather than deferring to system controls (for example, pure Dart implementations of the iOS toggle and the Android switch). Benefits: unlimited extensibility; no performance bottleneck switching between Flutter and platform code (the entire scene is composited at once); and decoupling from OS dependencies (the app looks and feels the same on all OS versions).

#### Composition

Widgets are composed of many small, single-purpose widgets. The number of design concepts is kept minimal while the vocabulary is large: in the widgets layer one concept (`Widget`) represents drawing, layout, user interactivity, state management, theming, animations, and navigation; in the animation layer `Animation`s and `Tween`s; in the rendering layer `RenderObject`s describe layout, painting, hit testing, and accessibility. The class hierarchy is deliberately shallow and broad. Even padding and alignment are separate components (to center a widget, wrap it in `Center`).

`Container` is made up of `LimitedBox`, `ConstrainedBox`, `Align`, `Padding`, `DecoratedBox`, and `Transform`. You can drill down into the source of any widget; rather than subclassing `Container`, compose it with other widgets or create a new widget using it as inspiration.

#### Building widgets

You determine a widget's visual representation by overriding `build()` to return a new element tree. The framework recursively asks each widget to build until the tree is entirely described by concrete `RenderObjectWidget`s, then stitches the renderable objects into a render object tree.

A build function should be free of side effects, and should return a new tree of widgets regardless of what it previously returned (it only needs to return something different if there is new configuration; if the configuration is the same, you can return the same widget). On each frame Flutter can recreate just the parts of the UI where state changed, so build methods should return quickly and heavy computation should be done asynchronously and stored as part of the state.

#### Widget state

- Stateless widgets (`StatelessWidget`) have no mutable state (for example, an icon or a label).
- Stateful widgets (`StatefulWidget`) store mutable state in a separate class that subclasses `State`; because the widget itself is immutable, a `StatefulWidget` has no build method, and its UI is built through its `State` object.

Whenever you mutate a `State` object you must call `setState()` to signal the framework to call the `State`'s build method again. The parent can create a new instance of the child at any time without losing the child's persistent state; the framework finds and reuses existing state objects.

#### State management

Constructors can pass data to children in a `build()` method:

```dart
@override
Widget build(BuildContext context) {
   return ContentWidget([!importantState!]);
}
```

As trees deepen, passing state up and down becomes cumbersome, so `InheritedWidget` provides an easy way to grab data from a shared ancestor. A widget reads it with:

```dart
final studentState = StudentState.of(context);
```

The `of(context)` call takes the build context (a handle to the current widget location) and returns the nearest ancestor of the matching type. `InheritedWidget`s offer `updateShouldNotify()`, which Flutter calls to determine whether a state change should rebuild dependent children. Flutter uses `InheritedWidget` extensively, for example for the app's visual theme; `MaterialApp`'s `build()` inserts a theme into the tree, and deeper widgets use `.of()` to look it up:

```dart
Container(
  color: Theme.of(context).secondaryHeaderColor,
  child: Text(
    'Text with a background color',
    style: Theme.of(context).textTheme.titleLarge,
  ),
);
```

As apps grow, many use utility packages like `provider` (a wrapper around `InheritedWidget`); the layered architecture also allows alternatives such as the `flutter_hooks` package.

### Rendering and layout

#### Flutter's rendering model

Traditional Android apps call into the Android framework's Java code, whose components draw themselves to a `Canvas` that Android renders with Skia. Cross-platform frameworks typically create an abstraction layer over the native Android and iOS UI libraries, often with app code in an interpreted language like JavaScript that must interact with the Java- or Objective-C-based system libraries, adding overhead. Flutter instead minimizes those abstractions and bypasses the system UI widget libraries in favor of its own widget set. The Dart code that paints Flutter's visuals is compiled into native code, which uses Impeller for rendering. Impeller ships with the application, so apps can pick up rendering improvements even if the phone has not been updated with a new Android version; the same is true on other native platforms such as Windows or macOS.

#### From user input to the GPU

The overriding principle of the rendering pipeline is that **simple is fast**.

#### Build: from Widget to Element

```dart
Container(
  color: Colors.blue,
  child: Row(
    children: [
      Image.network('https://www.example.com/1.png'),
      const Text('A'),
    ],
  ),
);
```

`build()` returns a subtree of widgets and can introduce new widgets as necessary. For example, `Container` inserts a `ColoredBox` when the color is not null:

```dart
if (color != null)
  current = ColoredBox(color: color!, child: current);
```

`Image` and `Text` might insert `RawImage` and `RichText`, so the eventual widget hierarchy can be deeper than the code (visible in the Flutter inspector in DevTools).

During build, Flutter translates widgets into an **element tree** with one element per widget. An element represents a specific instance of a widget at a location in the hierarchy. Two basic types:

- `ComponentElement`, a host for other elements.
- `RenderObjectElement`, an element that participates in the layout or paint phases.

`RenderObjectElement`s are an intermediary between their widget analog and the underlying `RenderObject`. An element can be referenced through its `BuildContext` (the `context` in `Theme.of(context)`, supplied to `build()`). Because widgets are immutable, any change creates a new set of widget objects, but the element tree is persistent from frame to frame, so Flutter can act as if the widget hierarchy were fully disposable while caching its underlying representation and rebuilding only the parts that require reconfiguration.

#### Layout and rendering

The base class for every node in the render tree is `RenderObject`, which defines an abstract model for layout and painting. It does not commit to a fixed number of dimensions or a Cartesian coordinate system. Each `RenderObject` knows its parent, but knows little about its children other than how to visit them and their constraints. `RenderParagraph` renders text, `RenderImage` renders an image, and `RenderTransform` applies a transformation before painting its child.

Most widgets are rendered by an object inheriting from `RenderBox`, a `RenderObject` of fixed size in a 2D Cartesian space; it provides the basis of a _box constraint model_ (minimum and maximum width and height).

To perform layout, Flutter walks the render tree depth-first and **passes down size constraints** from parent to child. The child must respect the constraints and responds by **passing up a size** within them. At the end of this single walk every object has a defined size and is ready to be painted via `paint()`. The box constraint model lays objects out in _O(n)_ time:

- A parent can dictate a child's size by setting maximum and minimum constraints to the same value (the topmost render object in a phone app constrains its child to the screen size).
- A parent can dictate the width but leave height flexible (or vice versa), as flow text does.

A child that needs to know how much space it has can use `LayoutBuilder`:

```dart
Widget build(BuildContext context) {
  return LayoutBuilder(
    builder: (context, constraints) {
      if (constraints.maxWidth < 600) {
        return const OneColumnLayout();
      } else {
        return const TwoColumnLayout();
      }
    },
  );
}
```

The root of all `RenderObject`s is the `RenderView`. When the platform demands a new frame (for example a vsync, or a completed texture decompression/upload), `compositeFrame()` on the `RenderView` creates a `SceneBuilder` to trigger an update of the scene. When complete, the `RenderView` passes the composited scene to `Window.render()` in `dart:ui`, which passes control to the GPU.

### Platform embedding

The engine is platform-agnostic and presents a stable ABI (`engine/src/flutter/shell/platform/embedder/embedder.h`) that provides a platform embedder with a way to set up and use Flutter. The embedder is the native OS application that hosts all Flutter content: it provides the entrypoint, initializes the engine, obtains threads for UI and rastering, and creates a texture Flutter can write to. It is also responsible for the app lifecycle, including input gestures (mouse, keyboard, touch), window sizing, thread management, and platform messages. Flutter includes embedders for Android, iOS, Windows, macOS, and Linux; custom embedders are possible (examples: fluttercast for VNC-style framebuffer remoting, flutter-pi for Raspberry Pi).

Platform-specific notes:

- As of Flutter 3.29, the UI and platform threads are merged on iOS and Android: the UI thread is removed and Dart code runs on the native platform thread.
- On iOS and macOS, Flutter is loaded into the embedder as a `UIViewController` or `NSViewController`. The embedder creates a `FlutterEngine` (host for the Dart VM and Flutter runtime) and a `FlutterViewController` that attaches to it to pass UIKit or Cocoa input events into Flutter and display frames rendered by the engine using Metal or OpenGL.
- On Android, Flutter is by default loaded into the embedder as an `Activity`. The view is controlled by a `FlutterView`, which renders Flutter content either as a view or a texture, depending on composition and z-ordering requirements.
- On Windows, Flutter is hosted in a traditional Win32 app, and content is rendered using ANGLE, a library that translates OpenGL API calls to DirectX 11 equivalents.

### Integrating with other code

#### Platform channels

A _platform channel_ (a name and a codec) is the mechanism for communicating between Dart code and the platform-specific code of the host app on mobile and desktop. Data is serialized from a Dart type like `Map` into a standard format, then deserialized into an equivalent in Kotlin (such as `HashMap`) or Swift (such as `Dictionary`).

```dart
// Dart side
const channel = MethodChannel('foo');
final greeting = await channel.invokeMethod('bar', 'world') as String;
print(greeting);
```

```kotlin
// Android (Kotlin)
val channel = MethodChannel(flutterView, "foo")
channel.setMethodCallHandler { call, result ->
  when (call.method) {
    "bar" -> result.success("Hello, ${call.arguments}")
    else -> result.notImplemented()
  }
}
```

```swift
// iOS (Swift)
let channel = FlutterMethodChannel(name: "foo", binaryMessenger: flutterView)
channel.setMethodCallHandler {
  (call: FlutterMethodCall, result: FlutterResult) -> Void in
  switch (call.method) {
    case "bar": result("Hello, \(call.arguments as! String)")
    default: result(FlutterMethodNotImplemented)
  }
}
```

#### Foreign Function Interface (FFI)

For C-based APIs, including those that can be generated for code written in modern languages like Rust or Go, Dart provides a direct mechanism for binding to native code using the `dart:ffi` library. FFI can be considerably faster than platform channels because no serialization is required. FFI is available for all platforms other than web, where the JS interop libraries and `package:web` serve a similar purpose. Create a `typedef` for each of the Dart and unmanaged method signatures and instruct the Dart VM to map between them, for example for the Win32 `MessageBox()` API:

```dart
import 'dart:ffi';

import 'package:ffi/ffi.dart'; // contains .toNativeUtf16() extension method

typedef MessageBoxNative = Int32 Function(
  IntPtr hWnd,
  Pointer<Utf16> lpText,
  Pointer<Utf16> lpCaption,
  Int32 uType,
);

typedef MessageBoxDart = int Function(
  int hWnd,
  Pointer<Utf16> lpText,
  Pointer<Utf16> lpCaption,
  int uType,
);

void exampleFfi() {
  final user32 = DynamicLibrary.open('user32.dll');
  final messageBox = user32.lookupFunction<MessageBoxNative, MessageBoxDart>(
    'MessageBoxW',
  );

  final result = messageBox(
    0, // No owner window
    'Test message'.toNativeUtf16(), // Message
    'Window caption'.toNativeUtf16(), // Window title
    0, // OK button only
  );
}
```

#### Rendering native controls in a Flutter app

Because Flutter content is drawn to a texture and its widget tree is internal, native views cannot be rendered interleaved with Flutter widgets. Platform view widgets (`AndroidView` and `UiKitView`) embed such content. On Android, `AndroidView`: copies the graphics texture rendered by the native view for composition; responds to hit testing and input gestures and translates them into native input; and creates an analog of the accessibility tree. There is synchronization overhead, so this suits complex controls like Google Maps where reimplementing in Flutter is impractical. Platform views can be integrated with other Flutter content (limitation: for example, transparency does not composite the same way as for other Flutter widgets). A typical use from the `google_maps_flutter` plugin:

```dart
if (defaultTargetPlatform == TargetPlatform.android) {
  return AndroidView(
    viewType: 'plugins.flutter.io/google_maps',
    onPlatformViewCreated: onPlatformViewCreated,
    gestureRecognizers: gestureRecognizers,
    creationParams: creationParams,
    creationParamsCodec: const StandardMessageCodec(),
  );
} else if (defaultTargetPlatform == TargetPlatform.iOS) {
  return UiKitView(
    viewType: 'plugins.flutter.io/google_maps',
    onPlatformViewCreated: onPlatformViewCreated,
    gestureRecognizers: gestureRecognizers,
    creationParams: creationParams,
    creationParamsCodec: const StandardMessageCodec(),
  );
}
return Text(
  '$defaultTargetPlatform is not yet supported by the maps plugin',
);
```

Communication with the native code typically uses platform channels. At present, platform views are not available for desktop platforms, but this is not an architectural limitation.

#### Hosting Flutter content in a parent app

Flutter content can be embedded into an existing Android or iOS app using the same embedding API (Android activity or iOS `UIViewController`). The Flutter module template can be embedded as a source dependency into an existing Gradle or Xcode build, or compiled into an Android Archive or iOS Framework binary. The engine takes a short while to initialize (load shared libraries, initialize the Dart runtime, create and run a Dart isolate, attach a rendering surface), so initialize it during app initialization or ahead of the first Flutter screen; a separate engine can be reused across multiple Flutter screens, sharing the memory overhead.

### Flutter web support

On the web, Flutter compiles your application code into either JavaScript or WebAssembly (when building with `--wasm`), rendering graphics using a WebAssembly build of the Skia engine. There is no need for Flutter to provide a Dart runtime; the framework and your code are compiled to JavaScript or WebAssembly. During development Flutter web uses `dartdevc` (incremental compilation; hot restart, and hot reload behind a flag). For production, `dart2js` or `dart2wasm` compiles the core, framework, and your app into optimized output deployable to any web server, optionally split into multiple files via deferred imports.

- Impeller availability by device: see the "Impeller availability" page linked from the original (https://flutter.dev/go/can-i-use-impeller) and the Impeller rendering engine page in the testing-performance references.
