# Architecture recommendations and resources

Architecture best practices, why they matter, and whether the Flutter team recommends them. Treat them as recommendations, not steadfast rules.

## Signature / Usage

Priority labels used on the page:

```text
* **Strongly recommend:** You should always implement this recommendation if you're starting to build a new application. You should strongly consider refactoring an existing app to implement this practice unless doing so would fundamentally clash with your current approach.
* **Recommend**: This practice will likely improve your app.
* **Conditional**: This practice can improve your app in certain circumstances.
```

## Notes

- Section intros: "You should separate your app into a UI layer and a data layer. Within those layers, you should further separate logic into classes by responsibility."; handling data with care "makes your code easier to understand, less error prone, and prevents malformed or unexpected data from being created"; good testing practices make adding new logic and UI "straightforward and low risk".
- Recommended resources: Compass app source code (`github.com/flutter/samples/tree/main/compass_app`), `very_good_cli`, Very Good Engineering architecture documentation, Flutter DevTools, and the `flutter_lints` package.
- Flutter app architecture (Dart, MVVM) is parallel to but distinct from the android-architecture skill's guidance.
