# Compile and cache ONNX models

Compilation converts an ONNX model into the hardware-specific binary an execution provider (EP) actually runs. Windows ML strongly recommends pre-compiling models targeting a hardware EP and caching the result to avoid repeated multi-second/minute cold starts, and validating a cached compiled model before reuse.

## Signature / Usage

```csharp
// Prepare compilation options
OrtModelCompilationOptions compileOptions = new(sessionOptions);
compileOptions.SetInputModelPath(modelPath);
compileOptions.SetOutputModelPath(compiledModelPath);

// Compile the model (one-time cost; cache the output)
compileOptions.CompileModel();
```

```python
model_compiler = ort.ModelCompiler(
    options,
    input_model_path,
    embed_compiled_data_into_model=True,
    external_initializers_file_path=None,
)
model_compiler.compile_to_file(output_model_path)
```

Validate a cached compiled model before reuse (Windows ML 2.3+):

```csharp
static bool IsCompiledModelOptimal(
    OrtEnv ortEnv,
    string compiledModelPath,
    string epName,
    IReadOnlyList<OrtEpDevice> epDevices)
{
    string compatibilityInfo =
        ortEnv.GetCompatibilityInfoFromModel(compiledModelPath, epName);

    return !string.IsNullOrWhiteSpace(compatibilityInfo) &&
        ortEnv.GetModelCompatibilityForEpDevices(
            epDevices,
            compatibilityInfo) ==
        OrtCompiledModelCompatibility.EP_SUPPORTED_OPTIMAL;
}
```

## Options / Props

| Concept | Description |
|------|-------------|
| Graph optimization | Fusion/constant-folding/layout work ONNX Runtime performs at session creation; cheap, EP-agnostic, runs every time |
| EP compilation | Conversion of the graph into an EP's own format + hardware-specific binary; expensive, done by hardware EPs (QNN, OpenVINO, VitisAI, NvTensorRtRtx, MIGraphX) via the `EPContext` mechanism, serialized to a `*_ctx.onnx` model or sidecar `.bin` |
| Ahead-of-time (AOT) compile | Compile at build/install time; best for controlled hardware and driver fleets or per-device installers. Needs cross-compilation tooling for targets the build machine can't run; validate on the target device and provide a recompilation fallback |
| Compile-on-first-run (recommended for broad distribution) | Check for a compiled artifact, compile if missing, cache and reuse; best for store apps / diverse consumer hardware; users pay the compile cost once on first launch |

| Compatibility API | Description |
|------|-------------|
| `GetCompatibilityInfoFromModel()` | Extract the EP-defined compatibility string from a compiled model file (upstream ORT 1.24) |
| `GetCompatibilityInfoFromModelBytes()` | Same, for a model already in memory |
| `GetModelCompatibilityForEpDevices()` | Validate the string against EP devices; returns `OrtCompiledModelCompatibility` (upstream ORT 1.23) |

| `OrtCompiledModelCompatibility` | Meaning | Recommended action |
|------|-------------|------|
| `EP_SUPPORTED_OPTIMAL` | Supported and optimal for the EP devices | Reuse the compiled model |
| `EP_SUPPORTED_PREFER_RECOMPILATION` | Supported, but the EP recommends recompilation for better performance | Can run; an optimal-only cache policy recompiles it |
| `EP_UNSUPPORTED` | Not supported by the current EP devices | Don't load it; recompile or use the original model |
| `EP_NOT_APPLICABLE` | EP gave no determination (also the default when the EP doesn't implement validation) | Not evidence of compatibility; use the original model unless the app has another validation policy |

## Notes

- Compile API (`OrtCompileApi` / `OrtModelCompilationOptions`) is available as of ONNX Runtime 1.22. The compiled-model compatibility APIs require Windows ML 2.3 or later.
- Compiled models are **device- and EP-specific** — bound to the exact EP they were compiled for.
- The compatibility string is generated by the EP at compile time, written to the compiled model's metadata properties as null-terminated UTF-8; its format is EP-defined and the app must not parse it.
- Flow: enumerate EP devices with `GetEpDevices()` and apply the same EP/device policy as for session configuration (non-empty collection, devices from the same EP) -> get the compatibility string (local model or remote metadata) -> `GetModelCompatibilityForEpDevices()` -> apply your cache/download policy. The Windows ML samples accept only `EP_SUPPORTED_OPTIMAL`.
- Validate before downloading: publish the opaque string as lightweight metadata next to the compiled model, check it first, and download the potentially large model only when the status meets your policy. Keep remote metadata paired with the exact artifact that produced it. `GetCompatibilityInfoFromModel()` parses the full `ModelProto` from disk, so use the remote-metadata pattern to decide before downloading.
- Under an optimal-only policy, treat missing compatibility metadata for the preferred EP as a cache miss. If compatibility evaluation errors, use the original model for that run and don't promote a newly compiled artifact.
- Events that may require a new cache entry: a new EP installed, GPU/NPU driver updated, hardware changed, source ONNX model changed, ONNX Runtime / EP / compilation settings changed.
- The compatibility APIs don't tell whether the artifact came from the current source model; include a source-model version or hash in the cache key and invalidate when compilation inputs change.
- Store compiled artifacts in a local per-device cache location (e.g. app local data folder); compilation can take minutes, so run it as a background operation to keep the UI responsive.
