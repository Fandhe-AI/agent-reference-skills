# App components overview

The four fundamental building blocks of an Android app, each an entry point through which the system or a user can enter the app.

## Signature / Usage

```xml
<manifest ... >
    <application android:icon="@drawable/app_icon.png" ... >
        <activity android:name="com.example.project.ExampleActivity"
                  android:label="@string/example_label" ... >
        </activity>
    </application>
</manifest>
```

## Options / Props

| Name | Type | Default | Description |
|------|------|---------|-------------|
| `Activity` | component | — | Entry point for user interaction; represents a single screen with a UI. Activated with `startActivity(intent)`. |
| `Service` | component | — | Background component for long-running operations without a UI. Activated with `startService(intent)` or `bindService(intent, connection, flags)`. |
| `BroadcastReceiver` | component | — | Receives system-wide broadcast announcements outside the normal user flow. Activated with `sendBroadcast(intent)`. |
| `ContentProvider` | component | — | Manages a shared set of app data accessible to other apps. Activated via `ContentResolver.query(uri, ...)`. |

## Notes

- All four component types must be declared in `AndroidManifest.xml` (`<activity>`, `<service>`, `<receiver>`, `<provider>`), which also declares required permissions, minimum API level, and hardware/software feature requirements.
- An `Intent` is the asynchronous message object used to activate most components (all except `ContentProvider`); it can be explicit (names a target component) or implicit (declares an action, letting the system resolve a matching component). See [Intent](./intent.md).
- `Service` and `BroadcastReceiver` are owned by the `android-background-work` skill; see that skill's reference for details. This page only introduces them as part of the four-component model.
- App resources (layouts, strings, drawables) are separate from source code and get a unique ID generated by the build tools (e.g. `R.drawable.logo`); alternative resources can target different device configurations via directory qualifiers (e.g. `res/values-fr/`).
