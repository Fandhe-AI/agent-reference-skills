# Fleet packages concepts

The `FleetPackage` declarative API in Config Sync deploys and manages fleet packages across clusters registered to a fleet. A package is a set of Kubernetes YAML manifests that define cluster configurations; updates roll out to the whole fleet at once or progressively. Each `FleetPackage` is defined once and updated with new revisions; the fleet package service detects a new revision and deploys it to the target clusters.

## Signature / Usage

### Requirements and limitations

- Only Git repositories are supported when configuring a fleet package.
- Kubernetes resources stored in Git must represent the end state of the resource (WET repositories); overlays that transform the resource are not supported.
- The `FleetPackage` API is available only in the `us-central1` region. Clusters in other regions can still be targeted, but Cloud Build and the gcloud CLI must be configured in `us-central1`.
- Maximum number of fleet packages: 300 per project per region.

### Architecture

The `FleetPackage` API uses Cloud Build to sync and fetch Kubernetes resources from the Git repository; the fleet package service then deploys those resources to the clusters.

### Example repository layout

```text
repo-root/
└── FleetPackages/
    └── clusters/
        ├── common-ingress.yaml
        ├── us-central1-a/
        │   ├── gke-1/
        │   │   ├── deployment.yaml
        │   │   └── service.yaml
        │   └── gke-2/
        │       ├── deployment.yaml
        │       └── service.yaml
        └── us-central1-b/
            ├── gke-1.yaml
            └── blue-green.yaml
```

### Variants selected by label

```yaml
resourceBundleSelector:
  cloudBuildRepository:
    # ... other fields
    path: "manifests"
    variantsPattern: "*" # Matches dev, staging, prod directories
variantSelector:
  variantNameTemplate: "${membership.labels['env']}"
```

With this configuration, a cluster labeled `env: staging` receives the contents of the `manifests/staging/` directory.

### Deployment to all clusters in a fleet

Rolling strategy, three clusters at a time, all clusters in the fleet:

```yaml
resourceBundleSelector:
  cloudBuildRepository:
    name: projects/my-project/locations/us-central1/connections/my-connection/repositories/my-repo
    tag: v1.0.0
    variantsPattern: "*.yaml"
    serviceAccount: projects/my-project/serviceAccounts/my-service-account@my-project.iam.gserviceaccount.com
target:
  fleet:
    project: projects/my-project
rolloutStrategy:
  rolling:
    maxConcurrent: 3
variantSelector:
  variantNameTemplate: deployment # matches a file named deployment.yaml
```

### Deployment to a subset of clusters

Label selector on the membership label `country` equal to `"us"`:

```yaml
resourceBundleSelector:
  cloudBuildRepository:
    name: projects/my-project/locations/us-central1/connections/my-connection/repositories/my-repo
    tag: v1.0.0
    variantsPattern: "*.yaml"
    serviceAccount: projects/my-project/serviceAccounts/my-service-account@my-project.iam.gserviceaccount.com
target:
  fleet:
    project: projects/my-project
    selector:
      matchLabels:
        country: "us"
rolloutStrategy:
  rolling:
    maxConcurrent: 3
```

## Options / Props

### FleetPackage fields that control variants

| Field | Description |
|-------|-------------|
| `resourceBundleSelector.cloudBuildRepository.variantsPattern` | Required. Glob pattern used to find files and directories in the Git repository (under `path`, or the repository root if `path` is omitted); determines which files or directories become variants and their content. |
| `variantSelector.variantNameTemplate` | Expression that maps each cluster in the fleet to one variant name generated by `variantsPattern`, based on the cluster's fleet membership metadata. |

### variantsPattern matching

| Match | Variant name | Variant content |
|-------|--------------|-----------------|
| YAML file | Filename without the extension (`prod-config.yaml` becomes `prod-config`) | Content of that single file |
| Directory | Directory name (`dev` becomes `dev`) | All YAML files in the directory and all subdirectories, recursively |

Pattern limitations: no recursive (double) wildcards (`**` is not supported); a pattern that includes a dot (`.`) must have an alphanumeric character after it; patterns can't include single quotes (`'`); variant names must be unique (`app1/deploy.yaml` and `app2/deploy.yaml` both create variant `deploy` and collide).

### Pattern examples for the layout above

| variantsPattern | Matches | Generated variants |
|-----------------|---------|--------------------|
| `"*"` | `common-ingress.yaml`, `us-central1-a`, `us-central1-b` | `common-ingress` (file), `us-central1-a` (all YAMLs in the folder), `us-central1-b` (all YAMLs in the folder) |
| `"*.yaml"` | `common-ingress.yaml` | `common-ingress` |
| `"us-*"` | `us-central1-a`, `us-central1-b` | `us-central1-a`, `us-central1-b` |
| `"us-central1-b/*.yaml"` | `us-central1-b/gke-1.yaml`, `us-central1-b/blue-green.yaml` | `gke-1`, `blue-green` |

### variantNameTemplate variables

| Variable | Value |
|----------|-------|
| `${membership.name}` | The cluster's fleet membership name |
| `${membership.location}` | The fleet membership location |
| `${membership.project}` | The fleet membership project |
| `${membership.labels['KEY']}` | Value of the label `KEY` on the fleet membership |

### variantNameTemplate examples

| Template | Behavior |
|----------|----------|
| `"${membership.labels['env']}"` | A cluster with label `env: prod` syncs to variant `prod` |
| `"${membership.location}"` | Clusters sync to variants matching their location (for example `us-central1-a`) |
| `"default"` | Clusters sync to a variant named `default`; this is the default if `variantSelector` is omitted. If the repository has no `default.yaml` file or `default` directory, nothing is synced. |

## Notes

- Benefits: automated rollout of the referenced resources to all clusters; new clusters added to the fleet automatically receive the package's resources; a maximum number of concurrently updated clusters limits the blast radius of an incorrect change; Cloud Build authenticates to Git once per project instead of once per `RootSync` or `RepoSync` object.
- Prefer Config Sync `RootSync` / `RepoSync` objects over fleet packages when you manage a small number of clusters, or need more control over deployment than the fleet package API provides with labels and variants.
- `variantsPattern` and `variantNameTemplate` must agree: the names your clusters resolve through `variantNameTemplate` must exist among the variants `variantsPattern` generates.
- The subset example omits `variantSelector`, so each matching cluster syncs to the variant `default`; with `variantsPattern: "*.yaml"` the repository root needs a `default.yaml`, otherwise nothing is synced (see the `"default"` row above).
- Fleet packages are Preview (stated in the quickstart tutorial, see [fleet-package-quickstart.md](./fleet-package-quickstart.md)).
- The gcloud command group is generated in `gcp-gke`; this page covers the concepts and workflow.
