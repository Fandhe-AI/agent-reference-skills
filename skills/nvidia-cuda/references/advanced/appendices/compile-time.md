# Improving CUDA Compilation Time

Techniques for measuring and diagnosing compile time bottlenecks (`-time`, `-fdevice-time-trace` flame charts, Compile Time Advisor), compiler flags that trade run time for compile time, and source code refactoring strategies for reducing the compile time of CUDA code.

## Signature / Usage

Per-phase compile time (`nvcc` and NVRTC accept `-time <filename>`; the output is appended to the end of the specified file). Sample output generated by NVRTC with the `-time` flag:

```text
File name, phase name, metric, unit
j4.cu.ptx, CUDA C++ Frontend, 30, ms
j4.cu.ptx, NVVM Optimizer, 1000, ms
j4.cu.ptx, PTX Translation, 14, ms
```

Source-centric view: `-fdevice-time-trace <filename>` (nvcc / NVRTC) produces a `.json` trace in the "Trace Event" format that can be opened with the Perfetto trace viewer (`https://ui.perfetto.dev/`). Compile Time Advisor, a command line tool that is part of the CUDA Toolkit, processes that `.json` file and writes a text summary. Source change: avoid code explosion from inlining a rarely called large function inside an unrolled loop (the fix is to mark `large_func` as `__noinline__`):

```cuda
__device__ int  large_func(int in) { ... } // a large function
__device__ void parent() {
  #pragma unroll
  for (int i = 0; i < 100; ++i) {
    if (unlikely_condition) {
          result += large_func(i); // <- Code explosion due
                                    // to inlining “large_func”
        }
      }
    }
```

Source change: disable unrolling with `#pragma unroll 1` on an outermost loop whose array index is thread-dependent (the array stays in local memory even when unrolled):

Adapted (not in the official docs): the index `i%threadIdx.x` of the official example is replaced by `(i + threadIdx.x) % 32`, which stays thread-dependent but avoids a division by zero for `threadIdx.x == 0`.

```cuda
int arr[32]{};

#pragma unroll    // problematic unroll for compile time
for(int i = 0; i < 32; ++i) {
  arr[(i + threadIdx.x) % 32] = large_func(i); // runtime dependent
                                      // index
}
...
#pragma unroll
for (int i = 0; i < 32; ++i) {
  result[i] = arr[i];
}
```

## Options / Props

| Flag | Description | Tool | Typical Usecase | Perf impact |
| --- | --- | --- | --- | --- |
| `--threads <N>` (`-t`) | Number of threads for compilation (maximum threads created in parallel when compiling for multiple architectures; ignored if `<N>` is 1 or for one architecture; `0` = number of CPUs). | nvcc | Multi-arch compilation with `--gencode`. | None |
| `--split-compile <N>` | Number of threads used for concurrent optimization (ignored if `<N>` is 1; `0` = number of CPUs). | nvcc, nvrtc, nvlink, nvJitLink, ptxas | Translation unit with multiple kernels or non-inlined device functions. | Minimal |
| `--split-compile-extended <N>` | Number of threads used for concurrent optimization. More aggressive form of split-compile. LTO-only. | nvcc, nvrtc, nvlink, nvJitLink | LTO (link time optimization) processing, where non-trivial run time slow down is acceptable. | Program-dependent |
| `--Ofast-compile <min/mid/max>` (`-Ofc`) | Device optimization levels: `max` (fastest compilation, many optimizations disabled), `mid` (balance, expensive optimizations disabled), `min` (minimal impact, some expensive optimizations minimized), `0` (disables fast-compile, the default). | nvcc, nvrtc, nvlink, nvJitLink, ptxas | Tradeoff modest to significant increase in run time for significant savings in compile time. | Program-dependent |
| `--gen-opt-lto` | Run the NVVM optimizer before saving LTO-IR. | nvcc, nvrtc | LTO-IR fragments are mostly self-contained; move optimization cost to build time instead of run time. | Program-dependent |
| `--pch` / `--use-pch <filename>` | Precompiled Header support. Automatic (`-pch`) and explicit (`-use-pch`). | nvrtc | Multiple programs being compiled that use a common header prefix, and frontend (parsing) time is a bottleneck. Forces frontend serialization, so may affect scaling with concurrent NVRTC invocations. | None |
| `--minimal` | Disable certain rarely used language features. | nvrtc | Frontend time is the bottleneck. | None |
| `--opt-level <N>` (`-O`) | Optimization level for ptxas (default: 3). | ptxas | Tradeoff significant run time increase for faster compile time. | Program-dependent |
| `--allow-expensive-optimizations=false` | Disallow aggressive optimizations (default: automatically turned on with optimization level >= 2). | ptxas | Tradeoff potentially significant run time increase for faster compile time. | Program-dependent |
| `--register-usage-level <0…10>` (`-regUsageLevel`) | Control aggressiveness of optimizations affecting register usage (default: 5). | ptxas | Tradeoff potentially significant run time increase for faster compile time. | Program-dependent |
| `--jobserver` | Enable GNU jobserver support. Prevents CPU oversubscription when concurrent compilation options and concurrent build commands (for example GNU make's `-j`) are used together. | nvcc, ptxas | Avoid oversubscribing the number of CPU cores. | None |

## Notes

- Workflow: measure compile time, apply flags or source changes for the dominant bottleneck, then repeat; improving compile time is typically an iterative process.
- Two ways to measure: compiler-centric (`-time` reports the breakdown across compilation phases such as parser and optimizer) and source-centric (`-fdevice-time-trace` flame chart breaks compile time down by source elements such as header files and template instantiations). The flame chart covers preprocessing, host and device code compilation, device linking, and binary generation.
- Compile Time Advisor gives five kinds of advice: Expensive Templates, Expensive Headers, Parallelizable Compilation (multiple `-gencode` targets compiled without `--threads`), Split Compilation (high optimization time that could benefit from `--split-compile`), and Compile Time Breakdown.
- The summary table in the source writes the flag as `--split-compile-extended`, whereas the detailed section heading for the same option reads `--extended-split-compile <N> (-split-compile)`; both appear in the official page and the table spelling is kept in the Options table above. Use the nvcc documentation to confirm the exact spelling for your toolkit.
- `--threads` / `--split-compile` / `--split-compile-extended` can be paired with `--jobserver` under GNU make or Ninja.
- `--pch`: using precompiled headers serializes frontend processing, which hurts scaling when several host threads invoke NVRTC concurrently; in that case experiment with turning PCH off.
- `--minimal` omits texture and surface functions and associated types (for example `cudaTextureObject_t`), CUDA Runtime functions provided by the `cudadevrt` device code library (for example `cudaMalloc`), kernel launch from device code, and types and macros associated with CUDA Runtime and Driver APIs provided by `cuda/tools/cudart/driver_types.h` (for example `cudaError_t`). The summary table says the savings are on the order of tens of milliseconds, whereas the detailed section says tens of microseconds; the official page is inconsistent.
- `--gen-opt-lto` runs the optimizer twice (during LTO-IR generation and again after linking), so the generated machine code may differ from the default LTO flow; check that performance has not degraded.
- User code and workflow changes: remove unused headers (for example `cuda_fp16.h` / `cuda_bf16.h` included unconditionally in generated NVRTC code), avoid excessive `__forceinline__` and apply `__noinline__` to rarely invoked large functions, avoid excessive loop unrolling (`#pragma unroll 1` on outermost loops with input- or thread-id-dependent array indices), invoke NVRTC / nvJitLink concurrently from multiple host threads for many programs, and when partitioning LLVM modules with `llvm::SplitModule()` inline aggressively first so that kernels do not call common device functions (otherwise all functions land in one module and no concurrent compilation is possible).
- The official page also contains images (flame chart examples) and a recommended-workflow figure that are not reproduced here.
- Section numbering: this page is Section 5.5 of the CPG; since 13.5 the Floating-Point Computation, Device-Callable APIs and CUDA C++ Memory Model appendices are Sections 5.6, 5.7 and 5.8.
- Source: https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compile-time.html (CPG v13.5, retrieved 2026-11-14)
- Adapted from the official docs: the official example indexes `arr` with `i%threadIdx.x` (division by zero for thread 0); the snippet above uses `(i + threadIdx.x) % 32` instead. The official text describes the index as thread-dependent (`i%threadIdx.x`).
