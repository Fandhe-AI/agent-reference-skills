# Claude apps gateway deployment and operations

Operational guide: identity-provider registration, container image build, Kubernetes/Cloud Run deployment, health probes, rate limits, drain on shutdown, JWT secret rotation, Postgres sizing, upgrades, and the security/threat model.

## Signature / Usage

```bash
# Container command
claude gateway --config /etc/claude/gateway.yaml

# Health probes
curl https://claude-gateway.internal.example.com/healthz   # liveness
curl https://claude-gateway.internal.example.com/readyz    # readiness (verifies store reachable)
```

Rate limits for large rollouts (`gateway.yaml`):

```yaml
rate_limits:
  device_authorization: { max: 1000, window_seconds: 600 }
  device_verify: { max: 1000, window_seconds: 600 }
```

Deliver `CLAUDE_STREAM_IDLE_TIMEOUT_MS` to developers through a gateway policy:

```yaml
managed:
  policies:
    - match: {}
      cli:
        env:
          CLAUDE_STREAM_IDLE_TIMEOUT_MS: "1800000"
```

Per-developer first-byte deadline (shell):

```bash
export CLAUDE_STREAM_FIRST_BYTE_TIMEOUT_MS=60000
```

JSON operational logs: set `CLAUDE_GATEWAY_LOG_FORMAT=json`; each line is then an object such as:

```json
{"severity":"INFO","time":"2026-11-04T17:03:21.512Z","message":"claude gateway listening on http://0.0.0.0:8080"}
```

## Options / Props

| Name | Type | Description |
| --- | --- | --- |
| `CLAUDE_GATEWAY_LOG_LEVEL` | env | `debug` / `info` (default) / `warn` / `error`; at `debug`, sign-in and refresh also log claim names (not values); doesn't affect always-emitted audit events |
| `CLAUDE_GATEWAY_LOG_FORMAT` | env | `json` writes operational logs as one object per line with `severity`, `time`, `message` (`warn` is written `WARNING`); audit events are unchanged (`ts` / `evt`, no `severity`). Requires Claude Code v2.1.319+ on the gateway server |
| `CLAUDE_GATEWAY_ALLOW_LOOPBACK` | env | Set to `1` to relax the SSRF guard's loopback block (and skip the boot-time metadata-endpoint warning) for every operator-configured URL; also required for a loopback OIDC issuer |
| `CLAUDE_GATEWAY_DRAIN_TIMEOUT_MS` | env | Drain window on `SIGTERM` / `SIGINT`; positive whole number of milliseconds (e.g. `120000`); other forms such as `120s` are ignored and the 25-second default stays. Draining requires gateway v2.1.274+ |
| `BUN_CONFIG_MAX_HTTP_REQUESTS` | env | Per-replica concurrent upstream request limit (default 256); whole number 1 to 65535; restart required |
| `CLAUDE_STREAM_IDLE_TIMEOUT_MS` | env (client) | Raise for long thinking pauses; default `300000`. Deliver via a gateway policy `env` block |
| `CLAUDE_STREAM_FIRST_BYTE_TIMEOUT_MS` | env (client) | Positive whole number of ms; limits how long the first attempt waits for response headers (otherwise 5 to 6 minutes). Requires Claude Code v2.1.307+ on the developer's machine |
| `API_TIMEOUT_MS` | env (client) | If lowered, keep above the gateway's time to first byte (see Notes) |
| `GET /healthz` | endpoint | Liveness probe; never reports not-ready |
| `GET /readyz` | endpoint | Readiness probe; fails if Postgres unreachable unless `store.readiness_grace_seconds` is set |
| `GET /.well-known/oauth-authorization-server` | endpoint | Returns `200` only after config load, OIDC discovery, upstream client construction, and Postgres migration succeed (end-to-end boot check) |
| `GET /protocol` | endpoint | Describes accepted paths/request shapes for the running version (not mentioned on this page; see the spend-limits page, v2.1.227+) |
| `GET /` | endpoint | Landing page showing the gateway version (also the `x-cc-gateway-version` header on `/managed/settings`) |

## Notes

- Network first: Claude Code refuses at sign-in a gateway whose hostname resolves to a public IP, even one the internet can't reach. Use a private address (RFC 1918 or CGNAT `100.64.0.0/10`) or, for public IPv4 space your organization owns, list the block in the `gatewayInternalNetworks` managed setting (gateway and user's machine must both be in that block; no single block containing both means give the gateway a private address). Otherwise contact your Anthropic account team.
- Deploy on the private network only; a trusted gateway can push settings that run commands on developer machines.
- Four ordered steps: IdP setup, Deployment, Operations, Security review.

### Identity provider setup

- Register a confidential OAuth/OIDC web app with a single redirect URI `https://<gateway>/oauth/callback`. The gateway authenticates to the IdP with the client secret or an uploaded certificate (certificate client authentication).
- Any OIDC-compliant IdP works (Okta, Microsoft Entra ID, Google Workspace, Keycloak, Dex, PingFederate, ...). Requirements: serves `/.well-known/openid-configuration` (HTTPS in production; an `http://` issuer is accepted, a loopback issuer additionally needs `CLAUDE_GATEWAY_ALLOW_LOOPBACK=1`); authorization-code flow (PKCE on by default, disable with `oidc.use_pkce: false`); `email` and optionally `groups` in the id_token, or from userinfo with `oidc.userinfo_fallback: true`. For private PKI set `oidc.ca_cert_pem`.
- Okta: the org authorization server returns a thin id_token without `email` / `groups`, so set `userinfo_fallback: true`; a custom authorization server such as `https://example.okta.com/oauth2/default` needs no fallback. `groups` is emitted only when the `groups` scope is in `oidc.scopes` and the app's groups claim filter allows it.
- Entra ID: `issuer` = `https://login.microsoftonline.com/<tenant-id>/v2.0`; groups are Object IDs (use GUIDs in `managed.policies.match.groups`, or App Roles); if roles arrive under `roles`, set `oidc.groups_claim: roles`.
- Google Workspace: `issuer` = `https://accounts.google.com`; no groups claim, so configure `oidc.google_groups` (Admin SDK Directory API, service account with domain-wide delegation) or use `oidc.allowed_email_domains` and `managed.policies.match.email_domain`. Google ignores `offline_access`; use `oidc.scopes: [openid, profile, email]` plus `oidc.extra_auth_params: { access_type: offline, prompt: consent }`.
- Refresh tokens drive silent renewal and deprovisioning (a disabled user's next refresh fails; session ends within `ttl_hours`). The gateway requests `offline_access` by default. Without refresh tokens, raise `session.ttl_hours` to `8` or `12` at the cost of deprovisioning latency.

### Deployment

- Single stateless Linux binary coordinating through Postgres. No separate license or per-seat fee (part of the `claude` binary). The gateway doesn't enforce that it's the only route to a model; closing bypass (e.g. blocking egress to `api.anthropic.com` except from the gateway) is a network policy decision, and breaks the WebFetch domain safety check unless `skipWebFetchPreflight: true` is set in the managed policy.
- Multiple gateways: separate deployments, each with its own config; the CLI stores trust and credentials per gateway hostname. Multiple OIDC issuers need separate instances.
- Serverless: Cloud Run works with `min-instances: 1` (avoids cold OIDC discovery); Lambda and Cloud Functions don't work (long-running HTTP server).
- Put an L7 proxy in front of plain-HTTP replicas and set `listen.trusted_proxies` to its source ranges; `X-Forwarded-For` is honored only when the TCP peer is trusted. Without it every request appears to come from the proxy IP (shared per-IP rate-limit bucket, proxy IP in audit events).
- Don't redirect the gateway's device-authorization and token endpoints (e.g. HTTP-to-HTTPS rewrite at the ingress): Claude Code doesn't follow redirects there, so sign-in and refresh break.
- Proxy idle timeout must exceed the gateway's keepalive interval: on every upstream except `provider: anthropic` the gateway writes an SSE `ping` after about 15 seconds of silence; on `provider: anthropic` it passes through the Anthropic API's own pings. The ALB default of 60 seconds suffices; the AWS example raises it to an hour anyway (gateways older than v2.1.229 sent no pings).
- Image: build around the native `claude` binary from a pinned release (see Install a specific version in the setup docs), verify against the GPG-signed `manifest.json` (Binary integrity and code signing), copy into the build context; mirror into an internal registry if needed. Needs a glibc-based image (musl images need the `linux-x64-musl` / `linux-arm64-musl` build), a writable state directory (set `CLAUDE_CONFIG_DIR`, e.g. `/tmp/.claude`), and the command `claude gateway --config /etc/claude/gateway.yaml` with the config mounted read-only and secrets as environment variables; listens on `listen.port` (default `8080`).
- Kubernetes: Deployment; config from a ConfigMap, secrets from a Secret (`${file:/path/to/secret}` or env vars); terminate TLS at the Ingress and set `listen.public_url` to its hostname; readiness probe `GET /readyz`, liveness `GET /healthz`. Prefer platform workload identity over static keys (cross-cloud pairings such as a Bedrock upstream on GKE need explicit credentials in the upstream's `auth` block).
- Cloud Run: leave `listen.port` at `8080` (or `port: ${PORT}`); `public_url` is normally an internal load balancer hostname because the `*.run.app` URL resolves to a public address (exception: `*.run.app` resolving privately via Private Service Connect plus a Cloud DNS private zone); mount the config as a secret volume; `min-instances: 1`.
- Push `forceLoginMethod`, `forceLoginGatewayUrl`, and `parentSettingsBehavior: "merge"` to developer machines via managed settings (MDM or per-OS `managed-settings.json`). Once deployed, Claude Code stops using a leftover API key or claude.ai login on the machine. Claude Desktop uses the `bootstrapUrl` equivalent in client-side managed settings.

### Large rollouts

- Sign-in is rate limited per client IP: 30 sign-in starts and 10 code submissions per 10 minutes. Causes of hitting it: the gateway can't see past the load balancer (fix `listen.trusted_proxies` first, then raise `rate_limits`), or many developers share NAT/VPN egress addresses.
- Sizing `max`: developers per egress address, estimate how many sign in per `window_seconds` (10 minutes default), then double it for retries and Claude Code plus Claude Desktop sign-ins. Example: 10,000 developers behind 4 addresses is about 420 per address per 10 minutes, doubled and rounded up to 1,000.
- `device_verify` stops guessing of sign-in codes; raise it only as far as needed. Without refresh tokens, developers re-sign in every `session.ttl_hours`; size for that steady rate and leave the limits raised.
- Claude Code v2.1.274+ shows `The gateway is limiting sign-in attempts right now`; a v2.1.274+ gateway shows `Too many attempts came from your network address` and logs a `sign-in refused` line naming the setting.

### Operations

- Logs go to stderr in two streams. Audit events (single-line JSON, always emitted): `config.load`, `session.mint`, `session.refresh`, `device.authorize`, `device.verify`, `device.callback`, `auth.denied`, `access.denied`, `access.public_client`, `inference`, `managed.serve`, `desktop_bootstrap.serve`, `desktop_bootstrap.denied`, `spend.blocked`, `admin.denied`, `admin.limit.upsert`, `admin.limit.delete`; also `guardrail.trace` (which filter fired, no matched text). `access.denied` reasons include `xff_unparseable` (event carries the unreadable `X-Forwarded-For` entry) and `client_ip_unknown` (no client IP). `access.public_client` fires once per process on the first request from a public address while `access_control.allow_cidrs` is empty. `desktop_bootstrap.denied` reasons: `not_configured`, `policy_not_opted_in`, `no_policy_matched`. `admin.denied` reasons: `invalid_key`, `bearer_rejected`, `no_credentials`. Operational logs are `[gateway]`-prefixed human-readable lines.
- Health: both probes are exempt from `access_control.allow_cidrs`. With `store.readiness_grace_seconds`, `/readyz` keeps reporting ready for up to that many seconds after the store stops answering.
- Concurrent upstream requests: each replica sends at most 256 requests upstream at once (a stream counts until it ends); extra requests wait inside the gateway for a slot (slow start or apparent hang; on `provider: anthropic`, waiting longer than `timeouts.upstream_ttfb_ms` gives up on that upstream, 502 if no later upstream serves it). The startup line containing `upstream requests:` shows the limit; a warning containing `client requests are open` is logged at most once a minute. Add replicas or raise `BUN_CONFIG_MAX_HTTP_REQUESTS`. A replica fills the limit at about limit / average seconds open (10 s average: about 26 requests per second). With CPU autoscaling, set the target below the CPU level at which that warning appears. Open requests hold memory (waiting requests keep their bodies), so size container memory for peak; an OOM-killed replica drops all its streams. In `load_test_mode`, requests don't wait at this limit but the warning is still logged.
- Keep `API_TIMEOUT_MS` above the gateway's time to first byte: for `provider: anthropic`, above the longest time the upstream takes to send its first event; for every other upstream, more than 20 seconds above the longest time to return response headers (the first keepalive `ping` comes about 15 seconds after the headers; gateways older than v2.1.229 send none, so use the anthropic rule). Also allow for waiting on a free slot, failover wait on a down upstream, and the longest non-streaming request.
- First-byte deadline: set `CLAUDE_STREAM_FIRST_BYTE_TIMEOUT_MS` (above your longest time to first byte, or healthy requests are aborted and re-sent). An unanswered re-send can wait 5 to 6 minutes until the body idle timeout. If you lowered `API_TIMEOUT_MS` only to retry sooner, remove it, or one unanswered re-send can end the turn with `No response from API`. Confirm with debug logging: search for `[first-byte] no response headers`.
- Outage behavior (Postgres down): existing sessions keep working (bearer tokens validate locally, refreshes don't touch the store, inference still served); new sign-ins fail (device flow and rate-limit counters live in Postgres); spend-limit enforcement fails open by default (configurable to fail closed); by default `/readyz` reports not-ready at once on every replica, so traffic to ready replicas only fails entirely, while `/healthz` keeps passing. IdP down: existing sessions work until `ttl_hours`; new logins fail; refresh succeeds after the IdP returns.
- Readiness grace: set `store.readiness_grace_seconds` longer than a failover (e.g. `300`); requests are unmetered during the outage with spend limits on and fail-open, while `enforcement.fail_closed_on_error: true` makes the gateway refuse inference with `429` `spend limit unavailable`. Requires Claude Code v2.1.282+ on the gateway server (earlier gateways refuse to start on the key; upgrade every replica first). Pointing readiness at `/healthz` also passes through outages but never reports not-ready.
- JWT secret rotation: generate a new secret, prepend it to the `session.jwt_secret` array, roll; after `ttl_hours` plus a margin, remove the old secret and roll again. Rotation is the only way to force sessions out (no per-session revocation); replacing the secret outright invalidates every session at once. For individual offboarding, deprovision in the IdP (session ends within `ttl_hours`).
- Postgres: real PostgreSQL (self-hosted or managed) at the minimum version; Postgres-protocol-only databases such as distributed SQL aren't supported. `store.postgres_url` takes one host (use the managed endpoint, load balancer, or VIP in front of multiple nodes). Tables: `kv` (device grants with 10-minute TTL and rate-limit counters; TTL per row), `spend` (per-principal period-to-date spend in cents; `admin.spend_retention_months`, default 13), `spend_limits` (until deleted via the API), `admin_audit` (`admin.audit_retention_days`, default 365), `principal_emails` (email, name, IdP groups; PII; `admin.identity_retention_days` since last activity, default 90), plus `_migrations`. A 30-second loop expires `kv` rows; an hourly sweep enforces retention. Without spend limits only `kv` is written. The database role needs create/alter rights (use a dedicated database or schema). With spend limits, back up regularly. To erase one departed developer: `DELETE FROM principal_emails WHERE principal = '<sub>'`.
- Connection pool: each replica opens up to `store.max_connections` (default 5). Keep replicas x `store.max_connections` at or below the database connections left (`max_connections` minus `superuser_reserved_connections`, default 3, minus other clients; managed services may reserve more). Count peak replicas including extras a rolling update starts (on Amazon ECS with default settings and on Cloud Run that can be as many again). Example: (6 + 2) x 5 = 40, versus 50 - 3 - 2 = 45 left. With spend limits on, keep the pool large enough or spend checks can time out (`spend check failed: spend precheck timed out`).
- Upgrades: replicas are stateless; the new binary self-migrates the database at boot (replicas serialize on a Postgres advisory lock). On `SIGTERM` (or `SIGINT`) the gateway stops accepting connections, lets in-flight requests finish for up to 25 seconds (drain window), then closes the rest; a second signal exits immediately. To give long streams more time on Kubernetes and Amazon ECS, raise `CLAUDE_GATEWAY_DRAIN_TIMEOUT_MS` and the orchestrator grace period (`terminationGracePeriodSeconds` / `stopTimeout`, default 30 s on both) together; keep the grace period at least 5 seconds above the drain window, plus any `preStop` hook duration on Kubernetes. Caps: ECS on Fargate `stopTimeout` max 120 seconds; Cloud Run stops an instance 10 seconds after `SIGTERM`. A cut drain logs a warning containing `drain window over after`.
- Rollback: migrations are append-only so an older binary is safe, but it re-validates the YAML against its older schema, so a config using a newer-only key fails boot; remove the new key first. Removing only the `groups` key from an upstream leaves it open to every developer (see "Roll back a gateway that uses groups" in the config reference). The image pin means fixes (including security) reach you only when you update the pin and redeploy.

### Security

- Data flow: inference goes CLI to gateway to your upstream (to Anthropic only if the Anthropic API is a configured upstream); OTLP telemetry (metrics, plus opt-in logs and traces) goes to your collector, never Anthropic; identity (email, groups, sub) goes IdP to gateway to CLI (with `forward_user_identity`, email and IdP subject are also sent as headers to your proxy); managed settings and the audit log never go to Anthropic.
- Threat model: developers hold short-lived JWTs, not raw upstream keys; CLI-to-gateway uses the RFC 8628 device grant and the IdP code exchange uses PKCE by default; the device-verification page enforces same-origin POST and per-IP rate limits (RFC 8628 section 5.1). Outbound requests to the IdP, OTLP collectors, and `provider: anthropic` upstreams pass an SSRF guard that resolves DNS, blocks link-local, cloud-metadata and (by default) loopback addresses, and pins the connection to the resolved IP; RFC 1918 ranges are deliberately allowed. For other providers the gateway rejects a `base_url` naming those addresses or a metadata hostname at config load, then the SDK connects without the DNS check. With proxy-only egress, that check moves to your forward proxy. If you add egress controls, the gateway must reach the metadata server when using instance-metadata credentials such as workload identity.
- Out of scope (your infrastructure to secure): a compromised gateway host (comparable to control over your MDM; the CLI's approval dialog for shell-capable settings limits silent changes) and a malicious OIDC provider.
- User code brute-force: `user_code` is 8 characters from a 20-character alphabet (about 2.56x10^10 combinations), expires after 10 minutes, and is per-IP rate-limited (`rate_limits`); limits apply to sign-in only, not inference.
- Compliance: the data plane sends nothing to Anthropic unless the Anthropic API is a configured upstream. `claude gateway` sends nothing to Anthropic; before v2.1.227 the host process sent startup telemetry (off with `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`) and one `HEAD` request at boot to `/api/hello` on `https://api.anthropic.com` (or `ANTHROPIC_BASE_URL`) unless a proxy variable or mTLS client certificate was set. While signed in to a gateway the CLI disables its own analytics, error reporting, and survey rating upload; before first sign-in it still sends startup events (deliver `DISABLE_TELEMETRY` in client-side managed settings to stop those). Transcript sharing writes a local file under `~/.claude/feedback-bundles/` instead of uploading. Developers' CLIs still send WebFetch hostname checks and version checks unless `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` and `skipWebFetchPreflight: true` are set. Pin client versions and set `DISABLE_UPDATES` to stop release fetches (`DISABLE_AUTOUPDATER` stops only background updates). Serve `public_url` over HTTPS (`listen.tls` or a TLS-terminating ingress; the gateway doesn't refuse plain HTTP); Postgres supports `?sslmode=require`; set `Strict-Transport-Security` at the ingress.
- Plugin marketplaces are fetched from each developer's machine, not through the gateway. On first interactive start the official marketplace `claude-plugins-official` is registered (catalog from `downloads.claude.ai`, fallback clone from `github.com`); `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` doesn't stop that. Use a `strictKnownMarketplaces` allowlist that omits it, a `blockedMarketplaces` entry, or `CLAUDE_CODE_DISABLE_OFFICIAL_MARKETPLACE_AUTOINSTALL` set to `"1"` in the managed `env` block, delivered in client-side managed settings as well as the policy's `cli` / `code` block (the first registration can precede sign-in).

### Troubleshooting

- Report with: gateway stderr plus redacted `gateway.yaml` and version (landing page `/`, `x-cc-gateway-version` header); for login issues `claude --debug-file ./claude-debug.txt` plus the audit log; for inference issues the model, upstreams, and audit log. Redact before posting publicly.
- Client-side symptoms: `/login` shows the standard picker instead of the Cloud gateway screen (managed settings keys missing); `Not signed in to the Cloud gateway — run /login.`; `Administrator policy requires a Cloud gateway sign-in on this machine` (`ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN`, an `apiKeyHelper`, or a saved Console key; `CLAUDE_CODE_USE_*` sessions start without sign-in); `Gateway login is configured in managed settings, but this Claude Code build does not include Cloud gateway support.` (update Claude Code); `Claude Code may not be enabled for your organization` after a 403 on `/managed/settings` (from `access_control` IP checks or a proxy/WAF; the gateway's own settings route never answers 403).
- Private-network check errors on `/login`: `Gateway hosts must be on your organization's private network; <host> resolves to the public (or unrecognized) address <ip>` (dual-stack names incl. AWS internal dual-stack ALBs); `Gateway login would go through proxy <proxy>, which is not on a private network` (add the gateway host to `NO_PROXY`); `Claude Code only signs in to <host> from inside its declared network <block> ...`; `Every address for gateway host <host> must be inside its declared network <block> ...`; `<host> is on the declared network <block>, which Claude Code checks over a direct connection, not through an HTTP proxy`; a message starting `gatewayInternalNetworks in managed settings` (validation rule broken; all new gateway logins refused on that machine until fixed; a block can be up to `/8` and overlapping entries are refused); `Could not resolve the configured HTTP proxy`; `Could not resolve gateway host <host>`.
- Sign-in rate limit: `The gateway is limiting sign-in attempts right now` (or `Request failed with status code 429` on older versions); audit events with `result: rate_limited` show the same few `client_ip` values. See Large rollouts.
- Desktop: bootstrap config couldn't be fetched when `/user/bootstrap` returns 404 (matching policy has no `desktop` key; an empty `desktop: {}` suffices). `auth.denied` with `reason: invalid_token` on `/v1/logs` or `/v1/metrics` comes from `otelHeadersHelper` (or, before Claude Code v2.1.307 in Desktop, an `Authorization` header in `OTEL_EXPORTER_OTLP_HEADERS`) in managed settings; remove it.
- Boot failures: config validation error naming `store.postgres_url` (for local dev use `docker run --rm -p 5432:5432 -e POSTGRES_HOST_AUTH_METHOD=trust postgres`); `store.postgres_url in <path> is not a URL the gateway can read` (before v2.1.290 a bare `Invalid URL` / `URI error`; multiple hosts or unencoded `/`, `?`, `#`, `%` in the password; use one host and `store.password`); `requires the native binary` (running under Node); OIDC discovery error after `config.load` (use `ca_cert_pem` for private PKI, `oidc.use_proxy: true` through a forward proxy, before v2.1.227 a direct route to the IdP, or Proxy-only egress on v2.1.277+); Postgres permission error (grant `CREATE` on the schema); `remaining connection slots are reserved` / `sorry, too many clients already` (see connection pool); `could not connect to Postgres at boot, attempt 1 of 3` (three attempts two seconds apart; raise `store.connect_timeout_seconds` if attempts time out); `Postgres <version> is below the supported floor` (gateway keeps running; upgrade the database, or on PostgreSQL 11, 12, 13 upgrade the gateway).
- OIDC: `/oauth/callback` shows "Sign-in could not be completed" (domain rejected, id_token validation failed, or `email_verified: false`, always rejected; set `oidc.email_claim` if the claim name differs); `id_token missing email claim` (only fires when `allowed_email_domains` is set; Okta custom server: add `email` claim, Entra: optional claim, PingFederate: OpenID Connect Policy, or `userinfo_fallback: true`); `refresh failed ... invalid_token (...) (at userinfo_no_id_token, ...)` with `Cloud gateway session expired` every `session.ttl_hours` (set `oidc.scope_on_refresh: true`, v2.1.260+; PingFederate: enable **Return ID Token On Refresh Grant** under **Applications > OAuth > OpenID Connect Policy Management**; stopgap raise `ttl_hours`); unknown or unsupported scope (set `oidc.scopes` exactly; must include `openid`; default `openid profile email offline_access`); sessions not renewing after overriding `oidc.scopes` (re-add `offline_access`); a `groups`-less developer gets `API Error: 400 you aren't in a group that can use this gateway. Ask your administrator to add you to one` when every upstream has a `groups` list (or list an upstream with no `groups` last; groups are re-read at the next token refresh).
- Network/TLS: Chrome blocks the Approve button on `form-action` CSP (add origins to `oidc.form_action_origins`); callback fails under `response_mode=form_post` (the gateway requests `response_mode=query`); login fails behind an ALB (set `listen.public_url` to the external `https://` origin); repeated trust prompt (TLS cert rotating per replica); `Could not verify the gateway's TLS certificate` / `SELF_SIGNED_CERT_IN_CHAIN` (OS trust store by default on the native binary and Node 22.15+, `CLAUDE_CODE_CERT_STORE`, or `NODE_EXTRA_CA_CERTS`); `Cloud gateway sign-in was not completed` (certificate fingerprint mismatch; message names the hostname and the first 16 characters of each fingerprint); `The gateway's TLS certificate changed during sign-in: it no longer matches the one you trusted`. After a gateway sign-in, if managed settings can't load, Claude Code names the reason and restarts in place; in a background session it ends the session and keeps the sign-in.
- Upstream credentials: every Amazon Bedrock request returns 502 with `Could not load credentials from any providers` on EC2 when IMDSv2's hop limit of 1 blocks the container (raise with `aws ec2 modify-instance-metadata-options --instance-id <id> --http-put-response-hop-limit 2`, or prefer ECS task roles); warning `upstream <name>: Google issued an access token that expires in <N>s` on an `external_account` credentials file (the token file must be renewed more than five minutes before expiry).
- `431` after sign-in: the session token lists IdP groups. The gateway answers `431` above 256 KiB of headers (or `limits.max_request_header_bytes` if set; before v2.1.284 above 16 KiB), with no log line or audit event. Upgrade, raise or remove the key, or have the IdP emit fewer groups, keeping groups used by `oidc.allowed_groups`, `admin.admin_groups`, `managed.policies` `match.groups`, upstream `groups`, and `rbac_group` spend caps.
- Long thinking: for non-`anthropic` upstreams, a proxy logging one request open for about 12.5 minutes then a run of `504`s means Claude Code ended a ping-only stream and re-sent without streaming (10 sends by default; non-streaming waits 300 s). Raise `CLAUDE_STREAM_IDLE_TIMEOUT_MS`; no longer proxy timeout needed. Confirm with `claude --debug-file ./claude-debug.txt` and search for `Error streaming, falling back to non-streaming mode: Stream idle timeout - no chunks received` (if `CLAUDE_CODE_DISABLE_NONSTREAMING_FALLBACK` is `1` the turn ends with `API Error: Stream idle timeout - no chunks received`). With the default `300000` a stream can stay on pings alone about 12.5 minutes; `900000` about 22.5; `1800000` about 37.5 (start with `1800000` if unknown). Fully silent connections still end after 5 to 6 minutes (the body idle timeout doesn't follow this variable). Restart the gateway after editing policy, then developers restart Claude Code. The `cli` key covers terminal, IDE extension, and Agent SDK; Claude Desktop's Code tab needs the `code` key (see "Choose `cli` or `code`").
- Long thinking on a `provider: anthropic` upstream (sole upstream): one request open about 20 minutes then `502` or `504`; non-streaming retries fail with a gateway `502` or the proxy's `504` when its timeout is below `timeouts.upstream_ttfb_ms` (no need to raise that). About 20 minutes at the default, 30 at `900000`, 45 at `1800000`. Same fix and delivery.
- Capacity: slow starts, hangs, or `502 all upstreams failed` at peak load with a `client requests are open` warning: add replicas or raise the per-replica limit.
