# environment-api

| Name | Description | Path |
|------|-------------|------|
| Application-Plugin Communication | `environment.hot` lets plugins communicate with application-side code for a given environment; the equivalent of client-server communication, but for environments other than the client. | [application-plugin-communication.md](./application-plugin-communication.md) |
| Custom Environment Instances / Backward Compatibility | Runtime providers can supply environments with proper defaults for their runtime; the existing Vite server API stays backward compatible with Vite 5. | [custom-environment-instances.md](./custom-environment-instances.md) |
| DevEnvironment class | During dev, each environment in a Vite server is an instance of `DevEnvironment`, reachable through `server.environments`. | [dev-environment-class.md](./dev-environment-class.md) |
| Environment Agnostic Code | Most code receives the current `environment` instance through its context, so accessing `server.environments` directly should be rare. | [environment-agnostic-code.md](./environment-agnostic-code.md) |
| Environment API Overview | Vite 6 formalizes Environments: instead of the two implicit ones (`client`, optionally `ssr`), an app can define as many environments as it needs to map how it runs in production. | [environment-api-overview.md](./environment-api-overview.md) |
| Environment in Build Hooks / Shared Plugins During Build | During build, plugin hooks receive the environment instance (replacing the `ssr` boolean), and all environments are built in a single process so the plugin pipeline can be shared as in dev. | [environment-build-hooks.md](./environment-build-hooks.md) |
| Environment Factories | Environment factories are implemented by runtime providers (not end users): they return `EnvironmentOptions` with defaults for a target runtime used in both dev and build, and can be built from the exposed `DevEnvironment` primitives. | [environment-factories.md](./environment-factories.md) |
| Environments Configuration | Configure multiple environments explicitly with the `environments` config option; each inherits the top-level options unless documented otherwise. | [environments-configuration.md](./environments-configuration.md) |
| Environments During Build (buildApp / createBuilder) | When the `builder` option is set, `vite build` builds the entire app: a `ViteBuilder` (the build-time equivalent of `ViteDevServer`) builds every configured environment, in series by default. | [environments-during-build.md](./environments-during-build.md) |
| FetchResult | `environment.fetchModule` returns a `FetchResult` consumed by the module runner: a union of `CachedFetchResult`, `ExternalFetchResult`, and `ViteFetchResult`. | [fetch-result.md](./fetch-result.md) |
| FetchableDevEnvironment | A `DevEnvironment` that communicates with its runtime via the Fetch API interface, through the standardized `handleRequest` / `dispatchFetch` pair. | [fetchable-dev-environment.md](./fetchable-dev-environment.md) |
| hotUpdate Hook | Lets plugins perform custom HMR update handling for a given environment. | [hot-update-hook.md](./hot-update-hook.md) |
| ModuleEvaluator | The interface a `ModuleRunner` uses to execute code that Vite transformed, and externalized modules. | [module-evaluator.md](./module-evaluator.md) |
| Separate Module Graphs (EnvironmentModuleNode) | Each environment has an isolated module graph with the same signature, so generic algorithms can crawl or query it independent of the environment. | [module-graphs.md](./module-graphs.md) |
| ModuleRunner | A module runner is instantiated in the target runtime and executes code processed by Vite. All APIs here are imported from `vite/module-runner` unless stated otherwise. | [module-runner.md](./module-runner.md) |
| ModuleRunnerOptions | Options passed as the first argument to `new ModuleRunner(...)`. | [module-runner-options.md](./module-runner-options.md) |
| ModuleRunnerTransport | The object a module runner uses to talk to its environment, via RPC or by directly calling a function; it must be coupled with a `HotChannel` on the server. | [module-runner-transport.md](./module-runner-transport.md) |
| Per-environment Hooks / configEnvironment | Plugin hooks are either global (called once for the whole server) or per-environment (called once per environment with `this.environment`). | [per-environment-hooks.md](./per-environment-hooks.md) |
| Per-environment State / applyToEnvironment | Because one plugin instance serves several environments, plugin state must be keyed by `this.environment`; `applyToEnvironment` selects or replaces the plugin per environment. | [per-environment-state-plugins.md](./per-environment-state-plugins.md) |
| raw DevEnvironment | When an environment implements neither `RunnableDevEnvironment` nor `FetchableDevEnvironment`, communication must be set up manually, via a virtual module or via `hot.send`. | [raw-dev-environment.md](./raw-dev-environment.md) |
| RunnableDevEnvironment | A `DevEnvironment` that can communicate arbitrary JavaScript values with application code: importing a module returns its real, live exports, so frameworks can run server entries directly. | [runnable-dev-environment.md](./runnable-dev-environment.md) |
