# CX Agent Studio Setup

Required setup steps to start using CX Agent Studio: a Google Cloud project with billing, the Gemini Enterprise for Customer Experience API and the Customer Experience Insights API enabled, optional audit logs, and (only if you use the API) the gcloud CLI, authentication and a client library.

## Signature / Usage

### Check for existing application default credentials

Adapted (not in the official docs): this check is not in the source. It asks gcloud for an access token from your Application Default Credentials (ADC) and discards it, so nothing is printed; success means that ADC exists and works.

```bash
if gcloud auth application-default print-access-token >/dev/null 2>&1; then echo "ADC found: reuse it"; else echo "No working ADC found"; fi
```

If it prints `ADC found: reuse it`, reuse that ADC and skip every login, quota project and cleanup step below. `gcloud auth application-default login` would replace it (gcloud 593.0.0 help: "Any credentials previously generated by gcloud auth application-default login will be overwritten."), and `set-quota-project` would change the project that every application reading it uses (help: "If a quota project already exists, it will be updated.").

### Use a dedicated gcloud configuration directory

Adapted (not in the official docs): otherwise, run all the steps below and the cleanup in one shell, after pointing gcloud at a new, empty configuration directory that only this setup uses, so your existing gcloud accounts and ADC are not read, replaced or revoked. The commands are for bash or zsh.

```bash
export CLOUDSDK_CONFIG="$(mktemp -d)"
```

Any later command or client library that needs these credentials must run with the same `CLOUDSDK_CONFIG`. gcloud, the Python google-auth and the Node.js google-auth-library read ADC from that directory; the Rust google-cloud-auth 1.19.0 does not, so for it also set `GOOGLE_APPLICATION_CREDENTIALS` to `"$CLOUDSDK_CONFIG/application_default_credentials.json"`. Other libraries were not checked.

### Initialize the gcloud CLI

```bash
gcloud init
```

### User account credentials for REST calls

If `gcloud init` already authorized the account you intend to use, you can skip `gcloud auth login`.

```bash
gcloud auth login
```

### Application default credentials for client libraries

`set-quota-project` requires that "The existing application default credentials must have the serviceusage.services.use permission on the given project" (gcloud 593.0.0 help); `roles/serviceusage.serviceUsageConsumer` includes it.

```bash
gcloud auth application-default login
gcloud auth application-default set-quota-project PROJECT_ID
```

### Cleanup

Adapted (not in the official docs): run this in the same shell, only if you created the dedicated directory above. Nothing is revoked or removed unless `CLOUDSDK_CONFIG` still holds an absolute path, so the revoke commands act only on the credentials stored in that directory.

```bash
case "$CLOUDSDK_CONFIG" in
  /?*)
    gcloud auth application-default revoke
    gcloud auth revoke --all
    rm -r -- "$CLOUDSDK_CONFIG"
    unset CLOUDSDK_CONFIG
    ;;
  *) echo "CLOUDSDK_CONFIG is not an absolute path: nothing revoked or removed" ;;
esac
```

## Notes

- Roles: selecting a project needs no specific IAM role; creating a project needs the Project Creator role (`roles/resourcemanager.projectCreator`, containing `resourcemanager.projects.create`); enabling APIs needs the `serviceusage.services.enable` permission, for example through Service Usage Admin (`roles/serviceusage.serviceUsageAdmin`) or the Owner role (`roles/owner`) if you created the project.
- APIs to enable: Gemini Enterprise for Customer Experience API (`ces.googleapis.com`) and the Customer Experience Insights API (`contactcenterinsights.googleapis.com`; the console text calls it "Contact Center AI Insights API").
- Enabling Data Access audit logs for the Gemini Enterprise for Customer Experience API can be skipped for non-production agent applications; together with Versions they track design-time changes.
- Installing the gcloud CLI, authentication and the client library can be skipped if you won't use the API. If you use an external identity provider, sign in to the gcloud CLI with your federated identity first.
- In Cloud Shell you are already logged in to gcloud.
- The source says: "The `GOOGLE_APPLICATION_CREDENTIALS` environment variable must not be set in order for your application default credentials to be used by client libraries." This applies to the user-account credentials that `gcloud auth application-default login` creates: ADC searches the `GOOGLE_APPLICATION_CREDENTIALS` environment variable first, then the credential file created by `gcloud auth application-default login`, then the attached service account from the metadata server, so a set variable takes precedence over that login file. Unset the variable only when you want client libraries to use the `gcloud auth application-default login` credentials; if it points to a credential configuration you rely on (for example Workload Identity Federation), keep it set. ADC in general is covered by the gcp-foundation skill.
- Source: https://docs.cloud.google.com/iam/docs/roles-permissions/serviceusage (`roles/serviceusage.serviceUsageConsumer`; retrieved 2026-11-14)
- Source: https://docs.cloud.google.com/docs/authentication/application-default-credentials (ADC search order; retrieved 2026-11-14)
- If you created the project with your user account you have the Owner basic role, which allows calling any API for the project; the source does not present this as a recommendation, so prefer granting narrower roles to other principals.
- Added (not in the official docs): the ADC check and the dedicated directory. In gcloud 593.0.0, `_GetGlobalConfigDir` returns `CLOUDSDK_CONFIG` when it is set, else `~/.config/gcloud` (`%APPDATA%\gcloud` on Windows) (`lib/googlecloudsdk/core/config.py`), and the bundled google-auth 2.62.0 reads `os.environ[environment_vars.CLOUD_SDK_CONFIG_DIR]` (`CLOUDSDK_CONFIG`) in `get_config_path` and joins it with `application_default_credentials.json` in `get_application_default_credentials_path` (`lib/third_party/google/auth/_cloud_sdk.py`). The Node.js google-auth-library 11.3.4 also reads `process.env['CLOUDSDK_CONFIG']` before the default (`build/src/auth/googleauth.js`), while the Rust google-cloud-auth 1.19.0 `adc_path` uses `GOOGLE_APPLICATION_CREDENTIALS`, else `$HOME/.config/gcloud` or `%APPDATA%\gcloud` (`src/credentials.rs`). Run with an isolated `HOME` and a `mktemp -d` `CLOUDSDK_CONFIG` (no real login), `gcloud info` reported that directory, `gcloud config set` wrote there, the bundled google-auth resolved the ADC path inside it, and the cleanup removed it while `$HOME/.config/gcloud` stayed unchanged; with `CLOUDSDK_CONFIG` unset, empty or relative, the cleanup ran no gcloud command.
- Adapted from the official docs: the source's cleanup runs `gcloud auth revoke` "If you called `gcloud auth login`" and `gcloud auth application-default revoke` "If you called `gcloud auth application-default login`"; without an account, `gcloud auth revoke` "revokes credentials for the currently active account". The page runs `gcloud auth revoke --all` (help: `gcloud auth revoke [ACCOUNTS ...] [--all]`, "Revoke credentials for all accounts.") and `application-default revoke`, which "Revokes Application Default Credentials that have been previously generated by gcloud auth application-default login and deletes the local credential file", inside the dedicated directory, then removes the directory.
- The source also shows Console steps and links to the client libraries page.
