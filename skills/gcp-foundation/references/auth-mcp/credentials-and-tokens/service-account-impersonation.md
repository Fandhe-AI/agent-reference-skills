# Service account impersonation

With impersonation you start with an authenticated principal (your user account or a service account) and request short-lived credentials for a service account that has the authorization your use case needs. It is used when your principal lacks the permissions you need, or you want to use a service account in a development environment.

## Signature / Usage

Impersonation is more secure than a service account key: it requires a prior authenticated identity and the credentials created do not persist, whereas a key needs no prior authentication and is a high-risk persistent credential if exposed.

### Before you begin

Enable the Service Account Credentials API (`iamcredentials.googleapis.com`) in your project (needs `serviceusage.services.enable`, e.g. via Owner or Service Usage Admin `roles/serviceusage.serviceUsageAdmin`). If using the gcloud CLI, ensure the API is enabled in the project you're operating in.

Required role: Service Account Token Creator (`roles/iam.serviceAccountTokenCreator`) on the service account (contains `iam.serviceAccounts.getAccessToken`). You must grant it to your account even in a project you created.

### Use the gcloud CLI: a specific command

```
gcloud storage buckets list --impersonate-service-account=SERVICE_ACCT_EMAIL
```

gcloud requests short-lived credentials for the service account and uses them for that command. The principal logged in to gcloud must have the required permission on the service account.

### Use the gcloud CLI: by default

```
gcloud config set auth/impersonate_service_account SERVICE_ACCT_EMAIL
```

Stop using impersonation by default:

```
gcloud config unset auth/impersonate_service_account
```

### Set up ADC for client libraries

Local ADC files created with impersonation are supported by client libraries in C#, Go, Java, Node.js, and Python on this page (the ADC local-development page also lists C++, PHP, Ruby, and Rust).

```
gcloud auth application-default login --impersonate-service-account SERVICE_ACCT_EMAIL
```

Credentials are then found automatically by the authentication libraries. Not all authentication libraries support local ADC files generated by impersonation (see ADC troubleshooting).

### Generate and manage short-lived credentials

If neither method fits (for example you need a credential type other than an access token, or need impersonation in production), generate and manage short-lived tokens yourself; see "Create short-lived credentials for a service account" in the IAM docs.

## Notes

- The language lists differ between the two source pages (this page: C#, Go, Java, Node.js, Python; the local-dev ADC page: C#, C++, Go, Java, Node.js, PHP, Python, Ruby, Rust). Both are recorded as published.
- Impersonation should always involve two principals (a caller and the impersonated service account). Self-impersonation creates a security vulnerability, since it lets a service account create an access token that can be refreshed in perpetuity.
