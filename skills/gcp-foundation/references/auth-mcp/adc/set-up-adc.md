# Set up Application Default Credentials

How you set up ADC for Cloud Client Libraries, Google API Client Libraries, and the REST and RPC APIs depends on the environment where the code runs. If you use API keys, you don't need to set up ADC.

## Signature / Usage

Environments (each section below):

- Local development environment
- Resource with an attached service account
- Containerized environment
- On-premises or another cloud provider
- Cloud-based development environment

### Local development: Google Account

Install the Google Cloud CLI. If you use an external identity provider (IdP), first sign in to the gcloud CLI with your federated identity (and run `gcloud init` after installation). In a local shell, create local authentication credentials for your user account (not needed in Cloud Shell):

```bash
gcloud auth application-default login
```

```bash
gcloud init
```

A sign-in screen appears. Afterward, credentials are stored in the local credential file used by ADC. To add scopes for services outside Google Cloud (such as Google Drive), create an OAuth Client ID and pass it with `--client-id-file`, specifying scopes with `--scopes`.

Tips for user credentials:

- ADC configured with a user account might not work for some APIs without extra steps. For "API not enabled" or "no quota project" errors, see the troubleshooting page.
- The local ADC file contains your refresh token. Any user with access to your file system can use it to get a valid access token. Revoke it when no longer needed with `gcloud auth application-default revoke`.
- The local ADC file is associated with your user account, not your gcloud CLI configuration. Changing gcloud CLI configuration might change the identity used by gcloud, but does not affect the local ADC file.

### Local development: service account impersonation

Impersonation-based local ADC files are supported in C#, C++, Go, Java, Node.js, PHP, Python, Ruby, and Rust. You need the Service Account Token Creator (`roles/iam.serviceAccountTokenCreator`) role on the service account.

```
gcloud auth application-default login --impersonate-service-account SERVICE_ACCT_EMAIL
```

Not all authentication libraries support local ADC files generated by impersonation (see troubleshooting).

### Local development: service account key

Use only if a user account or impersonation cannot be used. Create a service account with the roles your app needs and a key (see "Creating a service account key" in IAM docs), then set `GOOGLE_APPLICATION_CREDENTIALS` to the JSON file path. The variable applies only to the current shell session.

Adapted (not in the official docs): the rendered source wraps the placeholder in stray backticks; `KEY_PATH` is shown as a plain placeholder here.

Linux or macOS:

```bash
export GOOGLE_APPLICATION_CREDENTIALS="KEY_PATH"
```

```bash
export GOOGLE_APPLICATION_CREDENTIALS="/home/user/Downloads/service-account-file.json"
```

Windows PowerShell:

```bash
$env:GOOGLE_APPLICATION_CREDENTIALS="KEY_PATH"
```

```bash
$env:GOOGLE_APPLICATION_CREDENTIALS="C:\Users\username\Downloads\service-account-file.json"
```

Windows command prompt:

```
set GOOGLE_APPLICATION_CREDENTIALS=KEY_PATH
```

When the variable is set, ADC checks this location first, then other locations only if necessary.

### Resource with an attached service account

Services such as Compute Engine, App Engine, and Cloud Run functions support attaching a user-managed service account; the code on the resource then uses it as its identity. This is the preferred way to provide credentials to ADC for production code on Google Cloud. Many of these services also provide a default service account; using it is not recommended because it is highly privileged by default.

Ensure you have Create Service Accounts (`roles/iam.serviceAccountCreator`) and Project IAM Admin (`roles/resourcemanager.projectIamAdmin`). Then:

```bash
gcloud iam service-accounts create SERVICE_ACCOUNT_NAME
```

Grant a role to the service account (`ROLE` = role to grant):

```bash
gcloud projects add-iam-policy-binding PROJECT_ID --member="serviceAccount:SERVICE_ACCOUNT_NAME@PROJECT_ID.iam.gserviceaccount.com" --role=ROLE
```

Repeat for additional roles. In production, do not grant Owner, Editor, or Viewer; grant a predefined or custom role. Grant the principal that will attach the service account the Service Account User role:

```bash
gcloud iam service-accounts add-iam-policy-binding SERVICE_ACCOUNT_NAME@PROJECT_ID.iam.gserviceaccount.com --member="user:USER_EMAIL" --role=roles/iam.serviceAccountUser
```

`USER_EMAIL` is the email address for a Google Account.

### Containerized environment

- Local testing: configure the container to authenticate with your local ADC file (see "Local development: Google Account"). Test with a local Kubernetes implementation such as `minikube` and the `gcp-auth` addon.
- Cloud Run: call Google Cloud APIs with the service identity.
- GKE: access Google Cloud APIs from GKE workloads (Workload Identity Federation for GKE).
- GKE Enterprise: authentication overview and fleet Workload Identity Federation for GKE.
- Knative serving: Workload Identity Federation for GKE for Knative serving.

### On-premises or another cloud provider

The preferred approach is Workload Identity Federation: create a credential configuration file and set `GOOGLE_APPLICATION_CREDENTIALS` to point to it. It is more secure than a service account key. If you cannot configure Workload Identity Federation, create a service account, grant it required roles, create a key, and set `GOOGLE_APPLICATION_CREDENTIALS` as shown above.

### Cloud-based development environment

In Cloud Shell or Cloud Code, the tool uses the credentials from sign-in and manages authorizations. You cannot use the gcloud CLI to configure ADC there. To use a different user account or a service account, use a local development environment or a Google Cloud compute resource.

In Cloud Workstations, either:

- **Sign in using the Workstations UI**: user credentials are made available through the workstation's metadata server; libraries and tools retrieve them without a local file or `GOOGLE_APPLICATION_CREDENTIALS`. Because ADC checks `GOOGLE_APPLICATION_CREDENTIALS` and local credential files before the metadata server, ensure neither is set.
- **Authenticate manually**: run `gcloud auth application-default login` in the workstation terminal.

## Notes

- The gcloud CLI itself doesn't use ADC to access Google Cloud resources; `gcloud auth application-default login` only makes credentials available to client libraries. Provide credentials to gcloud via its own authentication.
- Service account keys are a security risk if not managed correctly; prefer keyless auth. Key creation might be disabled by organization policy (secure-by-default organizations). Keys acquired from an external source must be validated before use (externally sourced credentials requirements).
- In multi-user workstations, other users can access your OAuth access tokens; keep workstations single-user by default.
