# Guidelines for app help

General principles for deciding whether an app needs help content and how to design it well. Covers the three help formats (instructional UI, in-app help, external help) and when to reach for each.

## Signature / Usage

An intuitive, well-designed app is the first line of defense — no amount of help content fixes a confusing first impression. When help is warranted, all of it (regardless of format) should follow the same principles:

- **Easy to understand** — confusing help is worse than no help.
- **Straightforward** — present clear answers directly, not a maze to search through.
- **Relevant** — prefer contextual help tied to what the user is doing over a generic, hard-to-navigate index.
- **Direct** — links to feedback/bug-report/ToS pages may ride along with help, but only as an afterthought, never with equal or greater prominence than the actual answer.
- **Consistent** — help is part of the app's UI; it should follow the same usability, accessibility, and style guidance as the rest of the app.

## Options / Props

| Help type | Best for | See |
| --- | --- | --- |
| Instructional UI | Teaching a non-obvious gesture or surfacing a new/changed feature, without blocking progress | [Instructional UI](./instructional-ui.md) |
| In-app help | General-purpose help: help pages, contextual popups, feature descriptions | [In-app help](./in-app-help.md) |
| External help | Content too large for the app, or advanced tutorials/walkthroughs aimed at a minority of users | [External help](./external-help.md) |

## Notes

- Not every app needs dedicated help; decide per app, and per help type, rather than defaulting to all three.
- A user only seeks help once they already have a problem — so help content must resolve it quickly, or it will be ignored.
