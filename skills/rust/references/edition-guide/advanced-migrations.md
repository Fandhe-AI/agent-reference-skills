# Advanced Migration Strategies

How `cargo fix --edition` works and how to handle multiple configurations, large workspaces, broken fixes, macros, doctests, generated code, non-Cargo projects, and edition idioms.

## Signature / Usage

```console
# Keep partial (possibly broken) fixes for manual inspection
cargo fix --edition --broken-code

# Migrate all code behind Cargo features / for another target
cargo fix --edition --all-features
cargo fix --edition --target <triple>

# Apply idiom changes for the new edition
cargo fix --edition-idioms
```

Per-target edition in `Cargo.toml`:

```toml
[[bin]]
name = "my-binary"
edition = "2018"
```

## Notes

- The Edition Guide source writes `--force-warns`; the actual rustc flag is `--force-warn` (see rustc lints / command-line-arguments).
- Source: https://doc.rust-lang.org/edition-guide/editions/advanced-migrations.html (pinned: https://raw.githubusercontent.com/rust-lang/edition-guide/5a14f7276ebc0bd100974f02b918f30472c782fc/src/editions/advanced-migrations.md)
- The idiom lints are known to have problems and may make incorrect suggestions that fail to compile. Current idiom lints: Edition 2018 has `unused-extern-crates` and `explicit-outlives-requirements`; Edition 2021 has none. If problems occur, combine with `--broken-code` and resolve the rest manually.

### How migrations work

- `cargo fix --edition` runs the equivalent of `cargo check` with special lints enabled that detect code that may not compile in the next edition. The lints include instructions to make the code compatible with both the current and next edition.
- `cargo fix` applies the changes, then runs `cargo check` again to verify. If the fixes fail, it backs out the changes and displays a warning. It may repeat this until no new warnings are generated.
- Because the code is made compatible with both editions, you can iterate on the original edition before changing `Cargo.toml`.
- The lints belong to a lint group, e.g. `rust-2021-compatibility` for 2018 to 2021.

### Migrating multiple configurations

`cargo fix` works with a single configuration at a time.

- For `#[cfg]` platform-specific code, run `cargo fix` with `--target` for each target (may require moving code between machines without cross-compiling).
- For `#[cfg(feature = "...")]` code, use `--all-features`, or `--features` to migrate one feature at a time.

### Migrating a large project or workspace

- In a Cargo workspace, each package defines its own edition, so migrate one package at a time.
- Within a package, migrate individual Cargo targets with target selection flags. By default `cargo fix` uses `--all-targets`.
- For difficult cases, set `edition` per target in `Cargo.toml` (see above). This usually should not be required.

### Partial migration with broken code

- When a suggested fix fails, Cargo warns and by default backs out its changes. Use `--broken-code` to keep the changes and fix the remainder manually.
- To migrate incrementally, enable individual lints as warnings and run `cargo fix` (without `--edition`) or apply IDE "Quick Fixes". For example, add `#![warn(keyword_idents)]` to `src/lib.rs` / `src/main.rs` to apply only the 2018 keyword-conflict fixes.
- List lints per edition via the lint group page or `rustc -Whelp`.

### Migrating macros

- `cargo fix --edition` may not fix macros that generate syntax invalid in the next edition. `macro_rules` macros can sometimes be fixed if used within the same crate; proc macros generally cannot be fixed automatically.
- Example of a macro in a 2015 crate that breaks after migrating to 2018 without any warning (`dyn` becomes a keyword):

```rust
#[macro_export]
macro_rules! foo {
    () => {
        let dyn = 1;
        println!("it is {}", dyn);
    };
}
```

- Edition hygiene: tokens inside a macro are marked with the edition they come from, so a 2015-defined macro works when called from a 2018 crate. After changing the defining crate to 2018, the tokens are tagged 2018 and fail to parse; since the macro was never called in that crate, `cargo fix --edition` never inspected it.
- Recommended: fully test macro syntax, and test importing/using macros from crates of multiple editions.

### Documentation tests

`cargo fix` cannot update documentation tests. After changing the edition, run `cargo test` and fix failing doctests manually. In rare cases, set the edition per test with an annotation such as `edition2018` on the triple backticks.

### Generated code

Automated fixes cannot apply to Rust code generated by a build script at compile time; change the build script to generate compatible code manually.

### Migrating non-Cargo projects

Enable the migration lint group yourself, e.g. `#![warn(rust_2021_compatibility)]`, `-Wrust-2021-compatibility`, or `--force-warn=rust-2021-compatibility`. Then apply suggestions by:

- reading the warnings and applying them manually,
- using an editor/IDE that applies suggestions (e.g. VS Code with the Rust Analyzer extension "Quick Fix"),
- writing a migration tool with the `rustfix` library (used internally by Cargo to apply compiler JSON messages).

### Writing idiomatic code in a new edition

Idioms change over time. For example, in 2015 `extern crate rand;` is required in `src/lib.rs`; in 2018 it is no longer necessary. `cargo fix --edition-idioms` transitions such idioms.
