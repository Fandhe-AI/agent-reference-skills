# Use platform-specific APIs

How to reach platform-specific APIs from common code: prefer multiplatform libraries first, then expected and actual declarations, common interfaces with different injection strategies, or a dependency injection framework.

## Signature / Usage

Expected and actual function:

```kotlin
// In the common source set:
expect fun randomUUID(): String
```

```kotlin
// In the Android source set:
import java.util.*

actual fun randomUUID() = UUID.randomUUID().toString()
```

```kotlin
// In the iOS source set:
import platform.Foundation.NSUUID

actual fun randomUUID(): String = NSUUID().UUIDString()
```

Common interface with an expected factory function:

```kotlin
// In the commonMain source set:
interface Platform

expect fun platform(): Platform
```

```kotlin
// In the androidMain source set:
class AndroidPlatform : Platform

actual fun platform(): Platform = AndroidPlatform()
```

Dependency injection with Koin (expected module):

```kotlin
// In the common source set:
import org.koin.dsl.module

interface Platform

expect val platformModule: Module
```

```kotlin
// In the iosMain source set:
class IOSPlatform : Platform

actual val platformModule = module {
    single<Platform> { IOSPlatform() }
}
```

## Notes

- The official sample writes `actual fun platform() = AndroidPlatform()`; the inferred return type `AndroidPlatform` does not match `expect fun platform(): Platform`, so the return type is declared explicitly here.
- Before writing platform-specific code, check klibs.io for a multiplatform library (networking, logging, analytics, device functionality).
- Expected and actual declarations must be defined in the same package so they merge into one declaration. They work for functions, classes, interfaces, enumerations, properties, and annotations; this page focuses on functions and properties, which are most useful for simple cases.
- Do not include implementation code in the `expect` declaration.
- Options for injecting platform implementations of a common interface: expected and actual functions (the approach used by projects generated by the KMP IDE wizard), different entry points (construct implementations in platform modules, for example `application(AndroidPlatform())` from `Application.onCreate()` or `application(IOSPlatform())` from the SwiftUI `App` init), or a DI framework.
- If a DI framework is already used, the source recommends using it in simple cases too, rather than mixing two injection approaches. The interface can also be implemented in Swift in a platform module and provided through DI, but this is not very scalable because the Kotlin Multiplatform module is then not self-sufficient.
- Distance line: the `expect` / `actual` language mechanism itself is covered in expect-actual.md and by the kotlin skill; Android-specific APIs belong to android-platform-core and Apple APIs to apple-swift.
