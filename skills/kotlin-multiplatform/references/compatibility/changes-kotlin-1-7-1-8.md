# Compatibility guide for Kotlin Multiplatform — Kotlin 1.7.0−1.8.22

Incompatible changes that end their deprecation cycle and come into effect in Kotlin 1.7.0−1.8.22.

## Signature / Usage

Put the Gradle Java plugin in a separate, non-multiplatform subproject that depends on the multiplatform project:

```kotlin
plugins {
    id("java-library")
}
```

```kotlin
dependencies {
    implementation(project(":my-main-project")) // The name of your parent multiplatform project
}
```

## Changes

### Deprecated compatibility with Kotlin Multiplatform Gradle plugin and Gradle Java plugins

- Applying the Gradle Java, Java Library or Application plugins in the same project as the Kotlin Multiplatform Gradle plugin now gives a deprecation warning. The warning also appears when another plugin applies a Gradle Java plugin (for example, the Spring Boot Gradle Plugin automatically applies the Application plugin).
- Reason: Gradle's Java ecosystem plugins don't take into account that other plugins may publish or compile for the JVM target differently, have two JVM targets (JVM and Android) in one project, or have complex multiplatform structures with multiple non-JVM targets. Gradle provides no API to address this; workarounds are no longer possible since Gradle 8.8 (YouTrack KT-66542).
- At a minimum, compilation of Java sources and Gradle's `java-base` plugin remain supported within multiplatform projects.
- Best practice: determine whether you need the Gradle Java plugin; if it is used for a single task (for example creating a Javadoc JAR), define that task manually instead. Otherwise create a separate subproject, apply the Java plugin there, and add a dependency on the parent multiplatform project. The separate subproject must not be a multiplatform project and is only used to set up the dependency.

Example parent structure with `subproject-A`:

```text
.
├── build.gradle
├── settings.gradle.kts
├── subproject-A
    └── build.gradle.kts
    └── src
        └── Main.java
```

### New approach to auto-generated targets

Target accessors auto-generated by Gradle are no longer available inside the `kotlin.targets {}` block; use `findByName("targetName")`. Accessors such as `kotlin.targets.linuxX64` are still available.

```kotlin
// Before
kotlin {
    targets {
        configure(['windows',
            'linux']) {
        }
    }
}

// Now
kotlin {
    targets {
        configure([findByName('windows'),
            findByName('linux')]) {
        }
    }
}
```

- Kotlin 1.7.20 introduces an error when using target accessors in the `kotlin.targets {}` block (YouTrack KT-47047).

### Changes in Gradle input and output compile tasks

Kotlin compile tasks no longer inherit the Gradle `AbstractCompile` task with the `sourceCompatibility` and `targetCompatibility` inputs, making them unavailable in Kotlin users' scripts.

| Before | Now |
|--------|-----|
| The `SourceTask.stableSources` input is no longer available. | Use the `sources` input instead. Also, the `setSource()` methods are still available. |
| The `sourceFilesExtensions` input was removed. | Compile tasks still implement the `PatternFilterable` interface. Use its methods for filtering Kotlin sources. |
| The `Gradle destinationDir: File` output was deprecated. | Use the `destinationDirectory: DirectoryProperty` output instead. |
| The `classpath` property of the `KotlinCompile` task is deprecated. | All compile tasks now use the `libraries` input for a list of libraries required for compilation. |

- In Kotlin 1.7.20 inputs are not available, the output is replaced, and the `classpath` property is deprecated (YouTrack KT-32805).

### New configuration names for dependencies on the compilation

Compilation configurations got an extra `Compilation` postfix because the test compilation and its default source set previously shared configuration names. Projects and plugins that use old hard-coded configuration names no longer compile. Configuration names for dependencies on the source set stay the same. Available scopes: `Api`, `Implementation`, `CompileOnly`, `RuntimeOnly`.

| Item | Before | Now |
|------|--------|-----|
| Dependencies of the `jvmMain` compilation | `jvm<Scope>` | `jvmCompilation<Scope>` |
| Dependencies of the `jvmMain` source set | `jvmMain<Scope>` | `jvmMain<Scope>` (unchanged) |
| Dependencies of the `jvmTest` compilation | `jvmTest<Scope>` | `jvmTestCompilation<Scope>` |
| Dependencies of the `jvmTest` source set | `jvmTest<Scope>` | `jvmTest<Scope>` (unchanged) |

```kotlin
// Before
dependencies {
    add("jvmImplementation",
        "foo.bar.baz:1.2.3")
}

// Now
dependencies {
    add("jvmCompilationImplementation",
        "foo.bar.baz:1.2.3")
}
```

- In Kotlin 1.8.0 an error is introduced when using old configuration names in hard-coded strings (YouTrack KT-35916).

## Notes

- Migration (Kotlin 1.9 → 2.0): if upgrading from 1.7 or 1.8, also check changes-kotlin-1-9 and changes-kotlin-2-0-and-later.
- The Gradle Java plugin guidance here overlaps conceptually with the Gradle side covered by android-build-gradle only for the Android parts; Java / Application plugin details are Gradle-generic.
