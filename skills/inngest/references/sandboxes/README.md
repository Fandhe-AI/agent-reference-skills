# Sandboxes

| Name | Description | Path |
|------|-------------|------|
| Base images | The default Sandbox image includes Node.js, Python, Ruby, and common command-line tools, so you can run generated code or inspect a repository without building an image first. Pass `from` to choose another image. | [base-images.md](./base-images.md) |
| Cloning | Prepare a Sandbox once, snapshot it, and clone a separate Sandbox for each job. Each clone starts from the captured state with its own Sandbox ID. | [cloning.md](./cloning.md) |
| Commands | Run a command in a Sandbox as one durable step, then read its output as text, lines, or JSON. Every Sandbox has a `$` tagged template; each interpolated value is one argument, so there is no quoting to get wrong. | [commands.md](./commands.md) |
| Custom images | Build an image with Docker, upload the saved archive via the Builds API, wait for it to publish, then start Sandboxes from it with `image.custom()`. Selection (`image.custom()`) and building are separate operations; the SDK helper does not run `docker build`, upload a Dockerfile, or pull from a registry. | [custom-images.md](./custom-images.md) |
| Durable filesystems | A Sandbox keeps its local files through pause and resume, and a snapshot copies them into clones. Use an S3-backed persistent filesystem mount when different Sandboxes need the same backing files. | [durable-filesystems.md](./durable-filesystems.md) |
| Isolation and security | Run generated code in a separate Linux microVM with its own files, processes, and network identity, so that code cannot share your function's process. When called through `step.sandbox`, Inngest records the operation beside the function steps. | [isolation-and-security.md](./isolation-and-security.md) |
| Managed lifecycle | Coordinate Sandbox creation, commands, and cleanup as durable steps in a function run. Inngest records each operation's result, so a resumed function can continue after completed steps. | [managed-lifecycle.md](./managed-lifecycle.md) |
| Pause and resume | Pause a Sandbox while a job waits, then resume the same environment under the same ID without rebuilding its files. While paused, Inngest releases the live runtime and restores filesystem, memory, processes, environment, resources, network identity, and remaining runtime on resume. | [pause-and-resume.md](./pause-and-resume.md) |
| Sandboxes best practices | Run isolated code while keeping cleanup, retries, and results visible in your workflow. Record important results outside the Sandbox and plan cleanup before you create it, because destroying the resource removes its local files and processes. | [best-practices.md](./best-practices.md) |
| Sandboxes features | Index of Sandbox features. Use a Sandbox when generated code needs its own Linux environment; Inngest records Sandbox operations with your durable function steps. Pause and resume continue the same Sandbox; snapshot and clone start a new one from saved state. | [features-overview.md](./features-overview.md) |
| Sandboxes guides | Run isolated code, preserve work across lifecycle changes, and inspect failures in one durable run. This page is an index of the Sandbox guides: start, keep or branch work, access and inspect, and recover and clean up. | [guides.md](./guides.md) |
| Sandboxes limits | Choose a supported Sandbox size and plan tasks around the current beta limits for runtime, command output, tools, files, and snapshots. These limits apply to Sandboxes; workflow limits are separate. | [limits.md](./limits.md) |
| Sandboxes overview | Run generated code or test a project in a fully isolated microVM while a durable Inngest function coordinates the job. Sandboxes boot in under a second, can be paused and resumed, or snapshotted and cloned. | [overview.md](./overview.md) |
| Sandboxes quick start | Run a command in an isolated Linux Sandbox from a durable Inngest function, return its output, and destroy the Sandbox. The run trace shows each operation. | [quick-start.md](./quick-start.md) |
| Sandboxes reference | The current beta API calls and constraints for creating, running, and managing Sandboxes, from both the durable `step.sandbox` surface and the direct `inngest.sandboxes` client. | [reference.md](./reference.md) |
| Secrets | Let sandboxed code deploy, publish, push, and call your APIs without holding your long-lived keys. Anything in a Sandbox can be read by the code running in it, so prefer a tool, a short-lived token, or per-command `env` over injecting long-lived keys. | [secrets.md](./secrets.md) |
| Snapshots and restore | Prepare dependencies or files once, snapshot the Sandbox, and clone new Sandboxes from the snapshot for separate jobs. Each clone gets its own Sandbox ID and a copy of the captured local filesystem. | [snapshots-and-restore.md](./snapshots-and-restore.md) |
| SSH | Planned SSH access to inspect files or debug processes inside a running Sandbox. SSH is planned for launch; the current beta does not provide a supported public connection path. | [ssh.md](./ssh.md) |
| Tools | Let code in a Sandbox call back into your app. Each call is a durable step that runs with your credentials, so the Sandbox never sees your keys. | [tools.md](./tools.md) |
| Traces | Find failed or slow Sandbox operations alongside the other steps in a function run. Each `step.sandbox` call is a durable step: Inngest records its result for replay and applies that operation's retry classification. | [traces.md](./traces.md) |
