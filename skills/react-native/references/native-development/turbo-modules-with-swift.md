# iOS - Using Swift in Your Native Modules

How to write a Native Module with Swift business logic and a thin Objective-C++ glue layer (Adapter pattern). Starts from the iOS implementation of the Native Modules `NativeLocalStorage` guide.

## Signature / Usage

Swift module (`NativeLocalStorage.swift`):

```swift
import Foundation

@objcMembers public class NativeLocalStorage: NSObject {
  let userDefaults = UserDefaults(suiteName: "local-storage");

  public func getItem(for key: String) -> String? {
    return userDefaults?.string(forKey: key)
  }

  public func setItem(for key: String, value: String) {
    userDefaults?.set(value, forKey: key)
  }

  public func removeItem(for key: String) {
    userDefaults?.removeObject(forKey: key)
  }

  public func clear() {
    userDefaults?.dictionaryRepresentation().keys.forEach { removeItem(for: $0) }
  }
}

```

## Notes

- The core of React Native is mainly written in C++ and Swift/C++ interoperability is not great despite Apple's interoperability layer, so the module is not a pure Swift implementation: some Objective-C++ glue code is required, and the guide minimizes it. For migrating an existing legacy Native Module this approach should allow reuse of most of the code.
- Adapter pattern: business logic in a Swift module with a thin Objective-C++ layer. The Objective-C++ object is created by React Native, keeps a reference to the Swift module, handles its lifecycle, and forwards all method invocations to Swift.
- Declare all methods called from Objective-C as `public` with the `@objc` annotation (`@objcMembers` here), and make the class inherit from `NSObject`, otherwise it cannot be used from Objective-C.
- `"SampleApp-Swift.h"` is a header automatically generated by Xcode containing the public API of your Swift files in an Objective-C consumable format. The `SampleApp` part is your app name; change it if the app has a different name.
- Deviation from the official page: the official diff removes RCT_EXPORT_MODULE and adds +moduleName, but the iOS guide implementation this page starts from already has +moduleName and no RCT_EXPORT_MODULE, so moduleName is shown as an unchanged context line here.
- The `RCT_EXPORT_MODULE` macro is no longer required because native modules are registered through `package.json` (`codegenConfig.ios.modulesProvider`).
- The approach introduces a bit of code duplication in the interfaces but lets you reuse existing Swift code with little extra effort.
- The bridging header step is not required if you are a library author developing a native module distributed as a separate library. A bridging header is where you import all the Objective-C header files that need to be visible to Swift code; you may already have one.
- Finally, follow the last step of the Native Modules guide ("Build and run your code on a Simulator").
- Cross-skill: Swift language and Xcode project settings belong to apple-swift / apple-uikit; this page covers only the React Native module adapter.
