# GitHub Actions -- ワークフロー依存 lockfile (gh actions-lock)

ワークフローが依存する全アクションを検証済みコミットに固定する lockfile（`.github/workflows/actions.lock`）のリファレンス。

公式ドキュメント:
- https://docs.github.com/en/actions/concepts/security/workflow-dependency-lockfiles
- https://docs.github.com/en/actions/how-tos/secure-your-work/lock-workflow-dependencies
- https://docs.github.com/en/actions/how-tos/administer/enforce-workflow-lockfiles

---

## 概要

Workflow dependency lockfiles は public preview（変更される可能性がある）。

`uses: octo-org/deploy-action@v3` のようにタグ / ブランチで参照すると、実行時にその時点で指す commit に解決される。タグは移動できるため、レビューしたコードが実行される保証がない。lockfile は、ワークフローが依存する全アクション（推移的依存を含む）と reusable workflow に commit SHA を固定する。

- 再現可能なビルド
- 依存変更と Dependabot version update のレビュー
- CI/CD 依存の監査可能なインベントリ

lockfile は `.github/workflows/actions.lock` に置かれ、GitHub CLI 拡張 `gh actions-lock` が生成する。手で編集しない。ワークフロー単位または一括でオンボードできる。オンボード済みワークフローでは:

- 使う全アクション依存が lockfile に存在する必要がある
- 実行時と allowed actions ポリシーの検査には、固定された commit が使われる（この commit はソースリポジトリのいずれかのブランチ内に存在する必要がある）

lockfile は自リポジトリのワークフローを対象とし、推移的依存にも及ぶ。ただし reusable workflow 呼び出しの依存は除く（reusable workflow は、それが定義されているリポジトリの lockfile が対象）。

## 記録内容

```yaml
# This file is machine-generated by `gh actions-lock`.
# Do not edit by hand; run `gh actions-lock` to update.
version: 'v0.0.2'
workflows:
    '.github/workflows/ci.yml':
        - 'octo-org/deploy-action@v3.1.0'
dependencies:
    'octo-org/deploy-action@v3.1.0':
        ref: 'v3.1.0'
        commit: 'sha1-...'
        owner_id: 44036562
        repo_id: 197814629
```

| Key | Description |
|---|---|
| `workflows` | オンボード済みワークフローごとの依存一覧 |
| `dependencies` | 各参照が解決された commit |
| `ref` | ワークフローが使う参照（タグ / ブランチ） |
| `commit` | 参照が解決された正確な commit（実行されるコード） |
| `owner_id` / `repo_id` | ソースリポジトリの数値 ID。実行時に名前の指すリポジトリが固定時と同一か確認するために使う |

SHA pinning との比較: lockfile を採用したリポジトリでは、ワークフローファイル内の SHA pinning は不要。推移的依存に対応し、ワークフローが読みやすくなり、ソースリポジトリの identity を記録するため。

## 導入手順

1. 各ワークフローの `uses` が対応中・最新のバージョンを指すか確認する（reusable workflow の依存は定義元リポジトリの lockfile が対象なので、組織の共有ワークフローのリポジトリを先にオンボードすることを推奨）。Dependabot による Actions 依存の管理を先に有効化することを推奨。
2. 拡張をインストールする:

   ```bash
   gh extension install github/gh-actions-lock
   ```

   更新は `gh extension upgrade gh-actions-lock`。
3. リポジトリルートで生成する（引数なしで `.github/workflows/` 配下の全ワークフローをスキャンし、解決可能な各アクションを commit SHA に固定して書き出す）:

   ```bash
   gh actions-lock
   ```

   単一ワークフローだけオンボードする場合:

   ```bash
   gh actions-lock .github/workflows/ci.yml
   ```

   ローカルパスのアクションが未対応としてスキップされた場合、`uses: ./…` が実在のアクションファイルに解決されていない。ローカルパスは参照を含むファイルのディレクトリではなくリポジトリルートから解決される。全オプションは `gh actions-lock --help`。
4. 差分全体をレビューしてコミットする。拡張は lockfile 以外も変更する: ワークフローの `uses` を解決した具体的バージョンに書き換える（例: `octo-org/deploy-action@v3` → `octo-org/deploy-action@v3.1.0`、解決先 commit は不変）。自リポジトリのアクション参照も `uses: ./…` から `uses: $/…` に書き換えられる（ワークフローと in-repository の `action.yml` の両方）。`$/…` は常に実行中の commit に解決されるため lockfile エントリ不要。
5. 最新に保つ:
   - 依存を追加 / 削除したら `gh actions-lock` を再実行
   - Dependabot がオンボード済みワークフローのアクションを更新する際は、同じ PR で対応する lockfile エントリも再生成する。Dependabot はワークフローを新規オンボードしない（lockfile エントリが無いワークフローを更新した場合はオンボードが必要と報告するだけ）
   - `main` や `v3` のようなブランチ / 部分バージョンの参照は通常実行では再解決されない。タグが別の upstream commit を指すとエラーになる。正当な移動なら `gh actions-lock --relock`。最初に固定した commit が到達不能（force-push / 削除）の場合は `gh actions-lock --relock --accept-moved`

### 許可リストとの関係

リポジトリ / org / enterprise が許可アクションを指定している場合、オンボード後は許可リストが固定された commit SHA に対して検査される。`actions/checkout@v6` のようなタグ指定のエントリはもう一致しないため、ワイルドカードまたは完全な commit SHA を使う。

### レビュー観点

- `commit` の変更 = ワークフローが実行するコードの変更。通常の依存バージョン更新と同様に扱う
- `owner_id` / `repo_id` の変更は稀であるべき。名前の指すリポジトリが最初に固定したものではないことを意味するため、マージ前に調査する
- lockfile がおかしい場合はワークフローを直して再生成する。手動編集しない

## 組織での強制（Require lockfile ポリシー）

**Require lockfile** ポリシーは、アクション依存を含むが lockfile にオンボードされていない対象ワークフローの実行をブロックする。設定は「Governing execution of GitHub Actions workflows」の手順に従う。

段階的な導入:

1. パイロット: lockfile にオンボード済みの特定リポジトリ / ワークフローに絞る。**Evaluate** モードで開始し、Policy insights で結果を分析する。**Active** にするのは、全対象ワークフローで lockfile を最新に保つ仕組みが整ってから。
2. lockfile を最新に保つ自動化:
   - Dependabot version updates（同一 PR で lockfile エントリを再生成。新規オンボードはしない）
   - 専用ワークフロー: `.github/workflows/**` と `action.yml` / `action.yaml` の変更で起動し、push で lockfile を再生成してコミットする update ジョブ（`contents: write` が必要で、ブランチ保護 / ruleset が GitHub Actions の push を許可する必要がある）と、PR で `gh actions-lock --verify` を実行する verify ジョブ（lockfile が古ければエラー終了するため required check に適する）
   - Copilot skill（Copilot が編集した場合のみ対象のため、統制ではなく利便性）
   - pre-commit hook: `gh actions-lock --verify-local --no-fix`（オフライン・認証不要・高速。全依存に lockfile エントリがあることを確認するが、GitHub に対するピンの再検証はしない）
3. レビュー: `.github/workflows/actions.lock` を `CODEOWNERS` に追加し、branch protection / ruleset でコードオーナーの承認を必須にする。
4. 強制: **Require lockfile** ポリシーを **Active** に変更し、オンボード済みの全リポジトリ / ワークフローを対象にする。手順 2 の検証は残す（ポリシーは有効な lockfile が無い実行をブロックするが、verify は PR 作業中に古さを知らせる）。

ready-to-copy のワークフロー / skill 実装は `github/gh-actions-lock` リポジトリにある。

```bash
gh actions-lock --verify-local --no-fix
```

## Notes

- **Evaluate** モードは GitHub Enterprise でのみ利用できる。
- public preview のため仕様が変わりうる。lockfile の `version` は `v0.0.2`（公式例）。
