# Safeguard builds

Best practices for protecting builds that package code for deployment: use automated builds, generate build provenance, use ephemeral build environments, restrict access to the build service, protect credentials, manage dependencies and reduce opportunities to alter the build. Cloud Build is the managed build service on Google Cloud.

## Signature / Usage

### Submit a build with a build config

Cloud Build uses a build config file to provide build steps. The gcloud example below submits a build from a Cloud Storage source using a config file.

```bash
gcloud builds submit "gs://bucket/object.zip" --config=config.yaml
```

## Options / Props

### SLSA requirements named in the source (SLSA v0.1)

| SLSA level | Requirement |
|------------|-------------|
| 1 | Automated builds; build provenance available to consumers of built artifacts |
| 2 | Build service used instead of developer environments; provenance generated by (or readable directly from) the build service and verifiable for authenticity and integrity by a digital signature from the service that creates it |
| 3 | Provenance content also includes the entry point of the build definition and all build parameters under a user's control; Cloud Build provenance for container images provides SLSA level 3 build assurance |

### Practices and Cloud Build controls

| Practice | Cloud Build control |
|----------|---------------------|
| Automated builds (`cloudbuild.yaml`, Makefile, GitHub Actions workflow in `.github/workflows/`) | Build config file; integrates with Artifact Registry, Cloud Deploy, GKE, Cloud Run, GitHub and Bitbucket |
| Build provenance (digests of built images, input source locations, toolchain, duration) | Generated for container images |
| Ephemeral environment | New VM environment for every build, destroyed after the build |
| Least privilege and non-human identity | Minimum IAM permissions for organization members; customize the default Cloud Build service account or use a custom service account; Allowed integrations organization policy limits external services that can invoke build triggers; VPC Service Controls perimeter (supported only for builds that run in a private pool) |
| Protect credentials | Avoid hard-coded credentials in version control or build config; use Secret Manager secrets in builds |
| Dependencies | Review builders (public images, Cloud Build builders, community builders, custom builders, buildpacks) and create custom builders for more control; reference immutable versions, not tags such as `latest` or version ranges |
| Reduce opportunities to alter the build | No concurrent builds that influence each other; avoid extra user parameters beyond the entry point and top-level source location |

## Notes

- Local builds used for release let an attacker modify the build process and make builds hard to reproduce; the source recommends local builds only for debugging.
- Cloud Build security insights for built applications show the SLSA level, vulnerabilities, SBOM and VEX statements for build artifacts, and build provenance.
- Snippet taken from https://docs.cloud.google.com/sdk/gcloud/reference/builds/submit (gcloud 593.0.0 help). Cloud Build is covered by `gcp-devops` (planned).
- SLSA version: the level table follows SLSA v0.1 (the source links https://slsa.dev/spec/v0.1/requirements), where source, build and provenance requirements share levels 1 to 4. The current specification (SLSA v1.2, https://slsa.dev/spec/v1.2/) splits them into a Build track (Build L0 to L3, https://slsa.dev/spec/v1.2/build-track-basics) and a separate Source track (Source L1 to L4, https://slsa.dev/spec/v1.2/source-requirements); SLSA v1.0 removed the source aspects (https://slsa.dev/spec/v1.0/levels). Use the table to read the source page, not as a current conformance checklist (retrieved 2026-11-18).
