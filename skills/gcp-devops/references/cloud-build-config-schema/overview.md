# Cloud Build overview

Cloud Build executes your builds on Google Cloud: it imports source from repositories or Cloud Storage, runs a build to your specification as a series of build steps (each a Docker container), and produces artifacts such as Docker containers or Java archives. Its features meet the requirements of Supply chain Levels for Software Artifacts (SLSA) level 3.

## Signature / Usage

### Minimal build config

```yaml
steps:
- name: 'gcr.io/cloud-builders/docker'
  args: ['build', '-t', 'gcr.io/myproject/myimage', '.']
images: ['gcr.io/myproject/myimage']
```

### How a build works

1. Prepare application code and assets.
2. Create a build config file in YAML or JSON.
3. Submit the build to Cloud Build.
4. Cloud Build executes the build from the config.
5. Built artifacts, if any, are pushed to Artifact Registry.

## Options / Props

### Build step sources

| Kind | Description |
|------|-------------|
| Build steps provided by Cloud Build | Supported open-source builders for common languages and tasks (`GoogleCloudPlatform/cloud-builders`). |
| Community-contributed build steps | Open-source builders from the user community (`GoogleCloudPlatform/cloud-builders-community`). |
| Custom build steps | Your own builders. |

### Interfaces

| Interface | Use |
|-----------|-----|
| Google Cloud console | Build History page; Build Triggers to automate builds. |
| gcloud CLI | `gcloud builds` commands: submit, list, cancel builds. |
| REST API | Start builds, view status and details, list builds per project, cancel running builds. Requests use OAuth2 authorization. |

### Default pool vs private pools

| Aspect | Default pool | Private pool |
|--------|--------------|--------------|
| Environment | Secure hosted environment with public internet access; each build runs on its own isolated worker | Private, dedicated workers; hosted and fully managed, scale up and down to zero |
| Customization | Limited (machine type, disk space); limited private network access | Greater customization, including access to resources in a private network |

### Build security features

| Feature | Summary |
|---------|---------|
| Automated builds | All steps defined in a build config; automated builds are a SLSA level 1 requirement and using a build service rather than developer environments is a SLSA level 2 requirement. |
| Build provenance | Verifiable data about a build (digests of built images, input source locations, toolchain, duration); SLSA level 3 assurance for container images. |
| Ephemeral build environment | A new VM environment is set up for every build and destroyed afterwards. |
| Deployment policies | Integrate with Binary Authorization to block deployments of images not generated by Cloud Build. |
| Customer-managed encryption keys | CMEK compliance by default: the build-time persistent disk is encrypted with an ephemeral per-build key that is destroyed when the build completes and cannot be restored. |
| Security insights panel | Console panel showing SLSA level, vulnerabilities (scanned by Artifact Analysis), build details and build provenance. |

## Notes

- Each build step container is attached to a local Docker network named `cloudbuild`, so steps can communicate and share data.
- Standard Docker Hub images (for example Ubuntu, Gradle) can be used as steps. Cloud Build currently runs Docker engine version 20.10.24.
- Builds can be started manually (gcloud CLI or API) or by build triggers, which integrate with code repositories including Cloud Source Repositories, GitHub and Bitbucket. Cloud Source Repositories is unavailable to new customers since June 17, 2024 (End of Sale).
- Cloud Build is Google Cloud's managed build service; GitHub Actions workflows are in `github-docs`. Image building and Dockerfiles are in `docker`.
- Binary Authorization and Artifact Analysis are in `gcp-security`; private pool networking is in `gcp-networking`.
- The minimal example keeps the source's `gcr.io/myproject/myimage` image name. Container Registry was shut down on March 18, 2025: such names only work for `gcr.io` repositories hosted on Artifact Registry, so use `LOCATION-docker.pkg.dev/PROJECT/REPOSITORY/IMAGE` for new images.
