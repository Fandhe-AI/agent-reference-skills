# Direct3D / DirectX basics

| Name | Description | Path |
|------|-------------|------|
| ID3D11BlendState / ID3D11RasterizerState | `ID3D11BlendState` configures how the output-merger combines a pixel shader's output color with the value already in the render target (alpha blending, per-render-target write masks). `ID3D11RasterizerState` configures the rasterizer stage that converts primitives to pixels (fill mode, cull mode, depth bias, scissor clipping). | [d3d11-blend-rasterizer.md](./d3d11-blend-rasterizer.md) |
| Compute shaders (ID3D11ComputeShader, Dispatch, UAV) | Direct3D 11's compute pipeline runs general-purpose GPU work outside the graphics (vertex/pixel) pipeline. An `ID3D11ComputeShader` (compiled from HLSL with a `numthreads` attribute and a `[numthreads(x, y, z)]` entry point) is bound to the context and invoked with `Dispatch`; it reads/writes data through shader resource views and `ID3D11UnorderedAccessView`s (UAVs), which allow arbitrary read/write access (unlike read-only SRVs). | [d3d11-compute-shader.md](./d3d11-compute-shader.md) |
| ID3D11DepthStencilState / ID3D11DepthStencilView | `ID3D11DepthStencilView` binds a depth/stencil texture to the output-merger stage so the pipeline can perform depth testing (occlusion) and stencil testing (masking) during rendering. `ID3D11DepthStencilState` configures how those tests behave (comparison function, write mask, stencil operations) and is set on the context alongside the view. | [d3d11-depth-stencil.md](./d3d11-depth-stencil.md) |
| D3D11CreateDevice / ID3D11Device / ID3D11DeviceContext | `D3D11CreateDevice` creates the Direct3D 11 virtual-adapter device (`ID3D11Device`) and its immediate context (`ID3D11DeviceContext`). The device creates resources and state objects; the device context issues rendering commands. | [d3d11-device-context.md](./d3d11-device-context.md) |
| ID3D11Buffer / ID3D11Texture2D / ID3D11RenderTargetView | GPU resources in Direct3D 11 are buffers (`ID3D11Buffer`, for vertex/index/constant data) and textures (`ID3D11Texture2D`, for images and render targets). A resource view such as `ID3D11RenderTargetView` exposes a resource to a pipeline stage — here, as the output-merger's render target. | [d3d11-resources.md](./d3d11-resources.md) |
| ID3D11SamplerState / ID3D11ShaderResourceView (texture sampling) | `ID3D11ShaderResourceView` (SRV) exposes a texture (or buffer) to a shader stage as a readable resource; `ID3D11SamplerState` configures how a shader's `Sample`/`SampleLevel` HLSL intrinsics filter and address that texture. Both are bound to a shader stage — typically the pixel shader — alongside the shader itself. | [d3d11-sampler-srv.md](./d3d11-sampler-srv.md) |
| ID3D11VertexShader / ID3D11PixelShader / ID3D11InputLayout / Draw / DrawIndexed / OMSetRenderTargets | Shader-stage objects (`ID3D11VertexShader`, `ID3D11PixelShader`) and the input-assembler description (`ID3D11InputLayout`) configure the programmable pipeline; `OMSetRenderTargets` binds output targets; `Draw`/`DrawIndexed` submit rendering work on `ID3D11DeviceContext`. | [d3d11-shaders-drawing.md](./d3d11-shaders-drawing.md) |
| Important changes from Direct3D 11 to Direct3D 12, and hardware feature levels (D3D_FEATURE_LEVEL) | Direct3D 12 moves closer to hardware: apps take over synchronization, residency, pipeline state, work submission, and resource binding that D3D11 handled implicitly. Hardware feature levels (11_0 to 12_1) define GPU functionality sets selected at device creation. | [d3d11-to-d3d12-changes.md](./d3d11-to-d3d12-changes.md) |
| Direct3D 11 on 12: D3D11On12CreateDevice, ID3D11On12Device, wrapped resources | D3D11On12 lets D3D11 interfaces and objects drive the D3D12 API, so D3D11-based components (for example D2D text and UI) can work together with D3D12 components, and apps can be ported from D3D11 to D3D12 incrementally. | [d3d11on12.md](./d3d11on12.md) |
| D3D12 resource barriers and descriptor tables | Direct3D 12 makes the driver-hidden per-resource state tracking of D3D11 an explicit application responsibility. `ID3D12GraphicsCommandList::ResourceBarrier` submits one or more barrier descriptions — transition, aliasing, or UAV — that tell the GPU when it must synchronize access to a resource. Separately, a root signature's descriptor-table root parameters bind ranges of a descriptor heap (SRV/CBV/UAV/sampler) to shader-visible registers, set per draw/dispatch with `SetGraphicsRootDescriptorTable`/`SetComputeRootDescriptorTable`. | [d3d12-barriers-descriptors.md](./d3d12-barriers-descriptors.md) |
| D3D12 command lists and bundles: CreateCommandList, ID3D12CommandAllocator, ExecuteCommandLists, ID3D12Fence | Command lists record GPU commands; bundles are a second-level, reusable group of commands executed from direct command lists. Command queues submit direct/compute/copy command lists, and fences synchronize work between queues and the CPU. | [d3d12-command-lists-bundles.md](./d3d12-command-lists-bundles.md) |
| D3D12 debug layer, GPU-based validation, and DRED: ID3D12Debug1::SetEnableGPUBasedValidation, ID3D12DeviceRemovedExtendedDataSettings | Diagnostics for Direct3D 12: the debug layer (CPU-timeline validation), GPU-based validation (GBV, validation on the GPU timeline via patched shaders), and Device Removed Extended Data (DRED) for diagnosing device removal and GPU page faults. | [d3d12-debug-layer-dred.md](./d3d12-debug-layer-dred.md) |
| D3D12 Enhanced Barriers: ID3D12GraphicsCommandList7::Barrier, D3D12_BARRIER_GROUP, D3D12_BARRIER_LAYOUT | Enhanced Barriers is a newer synchronization model that runs alongside the legacy `D3D12_RESOURCE_BARRIER`/`ResourceBarrier` model. Instead of one `StateBefore`/`StateAfter` pair per barrier, it splits resource state into three independent axes — GPU pipeline synchronization scope (`D3D12_BARRIER_SYNC`), memory access type (`D3D12_BARRIER_ACCESS`), and, for textures only, image layout (`D3D12_BARRIER_LAYOUT`) — and submits them in typed groups (global/texture/buffer) through `ID3D12GraphicsCommandList7::Barrier`. Enhanced Barriers is not a hardware or driver requirement; support must be queried at runtime via `D3D12_FEATURE_DATA_D3D12_OPTIONS12::EnhancedBarriersSupported` before use. | [d3d12-enhanced-barriers.md](./d3d12-enhanced-barriers.md) |
| D3D12 memory management and residency: committed / placed / reserved resources, video memory budget, residency priorities | D3D12 memory management is "classify, budget and stream". Objects are resident when the GPU can access them; GPUs do not support page faulting, so apps must stay within the video memory budget. | [d3d12-memory-residency.md](./d3d12-memory-residency.md) |
| Direct3D 12 overview: Device, CommandQueue, GraphicsCommandList, PipelineState, RootSignature, Resource, descriptor heaps, fences | Direct3D 12 exposes the GPU pipeline explicitly. `ID3D12Device` creates every other object; `ID3D12CommandQueue` submits `ID3D12GraphicsCommandList`s recorded against an `ID3D12PipelineState` and `ID3D12RootSignature`; `ID3D12Resource` is memory the GPU/CPU read and write; `ID3D12DescriptorHeap` holds the views (RTV/SRV/CBV/UAV/sampler) bound to the pipeline; `ID3D12Fence` synchronizes CPU and GPU work. | [d3d12-overview.md](./d3d12-overview.md) |
| DirectX Raytracing (DXR): ID3D12StateObject / acceleration structures / DispatchRays | DirectX Raytracing adds a separate GPU pipeline for tracing rays against scene geometry. A raytracing pipeline is compiled into an `ID3D12StateObject` from DXIL libraries and hit-group subobjects (rather than a single `ID3D12PipelineState`); scene geometry is pre-processed into a two-level acceleration structure — a bottom-level (BLAS) per mesh and a top-level (TLAS) of instances referencing BLASes — built with `ID3D12GraphicsCommandList4::BuildRaytracingAccelerationStructure`. Rays are launched with `DispatchRays`, which invokes ray-generation, closest-hit, any-hit, and miss shaders addressed through a shader table. | [d3d12-raytracing.md](./d3d12-raytracing.md) |
| D3D12 render passes: ID3D12GraphicsCommandList4::BeginRenderPass / EndRenderPass | A render pass is a subset of the commands recorded into a command list, nested between `BeginRenderPass` and `EndRenderPass`. It lets the app declare output bindings and load/store dependencies so the driver can reduce off-chip memory traffic (notably on Tile-Based Deferred Rendering GPUs). New in Windows 10, version 1809 (10.0; Build 17763). | [d3d12-render-passes.md](./d3d12-render-passes.md) |
| D3D12 root signatures: D3D12_ROOT_SIGNATURE_DESC, root constants, root descriptors, descriptor tables, static samplers | A root signature is configured by the app and links command lists to the resources shaders require. It defines the types of data shaders expect (root parameters) but not the actual memory; the runtime values are root arguments. | [d3d12-root-signatures.md](./d3d12-root-signatures.md) |
| Variable-rate shading (VRS): RSSetShadingRate, RSSetShadingRateImage, D3D12_SHADING_RATE, SV_ShadingRate | Variable-rate shading (coarse pixel shading) lets a group of pixels be shaded as one unit, with the result broadcast to all samples in the group. The rate can vary per draw, per primitive, and (Tier 2) per screen-space image tile. | [d3d12-variable-rate-shading.md](./d3d12-variable-rate-shading.md) |
| Native DirectComposition (dcomp.h, IDCompositionDevice / IDCompositionVisual) | DirectComposition is a Win32 COM API (`dcomp.h`) for composing bitmap content — including DXGI swap chains and DXGI surfaces — into a retained-mode visual tree with hardware-accelerated 2D/3D transforms, effects, and animations, independent of the UI thread. It is the native predecessor to `Microsoft.UI.Composition`/`Windows.UI.Composition`; Microsoft's current guidance is to prefer those WinRT visual-layer APIs on Windows 10+ and to reach for native DirectComposition only from plain Win32/HWND apps that cannot host a `Compositor`. | [directcomposition.md](./directcomposition.md) |
| DirectX and WinUI 3 integration | WinUI 3 (Windows App SDK) desktop apps render DirectX content the same way UWP apps do — via `SwapChainPanel` and `ISwapChainPanelNative` — but the `SwapChainPanel` class lives in the `Microsoft.UI.Xaml.Controls` namespace instead of `Windows.UI.Xaml.Controls`, and getting the app window's native `HWND` (e.g. for a top-level `CreateSwapChainForHwnd` render surface) goes through the Windows App SDK's `IWindowNative` interop interface rather than `CoreWindow`. | [directx-winui3-integration.md](./directx-winui3-integration.md) |
| SwapChainPanel / ISwapChainPanelNative (DirectX and XAML composition) | `SwapChainPanel` is a XAML control that hosts a DirectX swap chain inside a XAML visual tree; unlike the older `SwapChainBackgroundPanel`, it can appear at any level of the tree and multiple instances can coexist. Native interop is done through `ISwapChainPanelNative`, obtained by querying the `SwapChainPanel` instance. | [directx-xaml-composition.md](./directx-xaml-composition.md) |
| IDXGIFactory2 / IDXGIAdapter | `IDXGIFactory2` creates DXGI 1.2+ swap chains (`CreateSwapChainForHwnd`, `CreateSwapChainForComposition`, `CreateSwapChainForCoreWindow`) and monitors stereoscopic 3D. `IDXGIAdapter` represents a display subsystem (GPU, video memory) that you enumerate to pick a rendering device. | [dxgi-factory-adapter.md](./dxgi-factory-adapter.md) |
| IDXGISwapChain1 / DXGI_SWAP_CHAIN_DESC1 / Present | A swap chain is a set of buffers used to present rendered frames to a window, `CoreWindow`, or composition surface. `IDXGISwapChain1` extends `IDXGISwapChain` with dirty-rectangle/scroll-rectangle presentation. You create it from `IDXGIFactory2` and describe it with `DXGI_SWAP_CHAIN_DESC1`. | [dxgi-swap-chain.md](./dxgi-swap-chain.md) |
| HLSL shader compilation: D3DCompile2 / DXC | HLSL source is compiled to shader bytecode before it is passed to `ID3D11Device::CreateVertexShader`/`CreatePixelShader` or embedded in a D3D12 `ID3D12PipelineState`. The legacy compiler API is `D3DCompile`/`D3DCompile2` (`d3dcompiler.h`, produces DXBC, shader model <= 5.1). For Shader Model 6.0+ (DXIL), use the DirectX Shader Compiler (`dxc.exe` / `dxcompiler.dll`) instead. | [hlsl-shader-compilation.md](./hlsl-shader-compilation.md) |
