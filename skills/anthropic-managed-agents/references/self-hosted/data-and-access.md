# Data and access in self-hosted Claude Managed Agents

What self-hosted Claude Managed Agents sends outside your network, where its log, traces, and metrics go, how long data is kept, who can reach the server, and how to keep tenants apart. The server connects to Anthropic only when the inference provider is the Claude API; Anthropic has no remote access to the server or its log.

## Signature / Usage

Adapted (not in the official docs): the source page has no code example; this `.env` line is built from its prose ("set `CMA_PUBLISH_ADDRESS` in `.env`"), with a placeholder address.

```text
CMA_PUBLISH_ADDRESS=<address-to-publish-port-8400-on>
```

Where the server listens:

| Listener | On by default | Default address | What it asks for |
|----------|---------------|-----------------|------------------|
| API requests | Yes | `127.0.0.1:8400` (same machine only); change with `server.addr` | A credential the server accepts |
| Console on your server | Yes (see Turn off the console in `./console.md`) | Same address and port as API requests | Nothing to load the page; to do anything, a person signs in through your identity provider |
| Prometheus metrics endpoint | No | `localhost:9464` (same machine only) | No credential |
| Listener for the egress gateway | No | Port 8410 on every interface | The gateway's key |

Docker Compose publishes port 8400 on `127.0.0.1`; to publish on another address set `CMA_PUBLISH_ADDRESS` in `.env`.

## Options / Props

Headers on model calls when the Claude API is the inference provider (IDs generated by your server; no setting turns them off; sent to a proxy or gateway named by `ANTHROPIC_BASE_URL`; never sent under any other provider):

| Header | What it holds |
|--------|---------------|
| `anthropic-managed-agents-session-id` | The ID of the session that the call serves |
| `anthropic-managed-agents-agent-id` | The ID of that session's agent |
| `anthropic-managed-agents-environment-id` | The ID of that session's environment |

Multitenancy:

| To keep apart | Do this |
|---------------|---------|
| Tenants | Give each tenant its own deployment, with its own database, server API key, and workers |
| Workloads at different trust levels | Give each trust level its own deployment, set up as for a tenant (e.g. trusted and untrusted code, or workers that reach systems only some callers may use) |
| Callers in a deployment | Turn on single sign-on, map groups to the `developer` or `user` role, and keep the server API key for administrators |

### Every connection that the server makes

- Your inference provider
- The server's database
- Services that issue the server's credential for model calls, if it gets that credential from a service
- A cloud provider's service for listing models, if your inference provider lists models on a separate service
- The MCP servers that you allow
- The Git hosts that you allow, for repositories that sessions use
- An OpenTelemetry collector, if you configure one
- The identity providers you list for single sign-on, if any
- A secret manager or key management service, if you configure one, and the services that issue the server's credential for it
- Any other service that you configure the server to call

## Notes

- Distinct from `self_hosted` environments / self-hosted sandboxes (workers; `../environments/self-hosted-sandboxes*.md`): here you host the whole service (server, database, workers) and store session transcripts yourself; with self-hosted sandboxes Anthropic hosts the service (and stores transcripts) and you host only the tool-execution worker. Access to self-hosted Claude Managed Agents is requested through your Anthropic account team.
- Default inference provider is the Claude API; with another provider, model calls go there instead. Where the provider offers web search and web fetch, it runs them; the tools are off until turned on in the server's settings.
- To check traffic, compare your egress proxy or firewall log with the list above. Workers are separate: a worker has whatever network access you allow its container, VM, or sandbox, and every command an agent runs has the same access. The optional egress gateway connects to the hosts you list for it and sends them stored credential values.
- Each model call carries the conversation so far, including prompts, tool inputs, and tool results. IDs hold no name or content but encode the creation time. With the Claude API, the server also validates its credential at startup and every 60 seconds (unless you change `health.check_interval`); these checks run no inference and carry none of the three headers.
- Every request to the Claude API has a `User-Agent` header naming the server software and version; the API key identifies your organization. Model calls can carry the label `cma-server` as `metadata.user_id` in the request body: sent for calls to the Claude API, Microsoft Foundry, and a model gateway that accepts the same requests as the Claude API; never sent to Amazon Bedrock, Claude Models on Google Cloud (Google managed), or a model gateway that takes another request format. A proxy or gateway of your own must accept `metadata.user_id` in the request body or every model call fails.
- Logs go to standard error (collected by Docker, Kubernetes, or the service manager). No traces or metrics are recorded until you turn them on with the standard OpenTelemetry environment variables; a Prometheus endpoint can also expose metrics (if `OTEL_METRICS_EXPORTER` is `prometheus` with no address it uses the default address; via the server Helm chart it listens on port 9464 of every server pod, reachable by anything with a route unless a NetworkPolicy blocks it).
- Retention: your log pipeline, collector, and tracing backend determine retention of logs, traces, and metrics; the server keeps no log files. Everything else is in your database (in memory, erased on restart, if no database is set up). With a secret manager configured, the secret of each new vault credential is kept there instead of the database; earlier secrets stay in the database.
- Sessions stay until you delete them; the server doesn't delete by age. Deleting through the API removes the session and history but the server keeps the session's ID, may refuse while the session is running, and doesn't reach backups, exported logs and traces, or memory store content. On Kubernetes the session's `/workspace` volume stays in place.
- Model data falls under your organization's agreement with the provider (with the Claude API, your data retention agreement and settings; a zero data retention arrangement covers these model calls like other Messages API calls). The API and data retention page lists Claude Managed Agents as not covered by ZDR because when Anthropic runs the service it stores transcripts until you delete them; with self-hosted Managed Agents you store them yourself.
- Credentials the server accepts are never issued or held by Anthropic: ones you set or created, ones your identity provider issued, or ones the server generated (such as the token handed to a worker with each piece of work). The server never connects to a worker; applications and workers connect to the server.
- Egress gateway listener speaks plain HTTP and its answers carry stored credential values; the Compose stack and the server Helm chart let only the gateway reach it. If you run the server another way, do the same. Run Docker Engine 28.3.3 or later; under some earlier releases machines on the local network can reach a loopback-published port.
- Roles limit only requests a caller makes with their own token. Code an agent runs can call the server with any credential its sandbox holds, and an environment key can read events and post tool results in every session in its environment. Run each session in its own sandbox and keep the environment key out of it (the Compose and Kubernetes stacks do this). The server API key reaches every environment.
- Secret manager, single sign-on, model gateway: keep deployments apart in each. For single sign-on give each deployment `audiences` entries no other deployment lists, give a role only to callers allowed at that level, and set no `default_role`. For a model gateway give each deployment its own value for a header such as `x-tenant-id` under `inference.headers`.
