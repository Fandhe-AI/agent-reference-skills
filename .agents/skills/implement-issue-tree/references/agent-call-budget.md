# エージェント呼び出し数の予算

本書は implement-issue-tree スキルの一部。全体は ../SKILL.md 参照。

Workflow ランタイムは 1 ランあたりのエージェント数に上限を持つ。上限に達したランは `completed` として返るため、
予算を持たないスクリプトは PR 作成直後の未監視のまま終わる（Issue #592）。本書は上限値の根拠、数え方、
新規着手を止める式、止めたあとに返す情報をまとめる。実装は `scripts/implement-issue-tree.src.js` の
`agentBudget` 宣言部（定数・`agentBudgetHold`）と駆動部冒頭の `wrapAgentCounting` による差し替え。

## 上限値 1,000 の根拠

| 根拠 | 内容 |
|------|------|
| ドキュメント | `references/subagents/workflows.md`（anthropic-claude-code-extend スキル）の `Max agents per run \| 1,000` |
| 実測 | 2026-10-11〜12 の `Fandhe-AI/fandhe-container`（`parent` = ルート・total 1,077、`parallel: 5`）。`agent_count` 1000・`agents_done` 1000・`agents_error` 0 で `completed` 終了。最後に起動されたエージェントは `pr-create:#543` で、その後の monitor・merge は起動されなかった |

内訳（ラベル別。上位）: `worktree:residual-bytes` 269・`state:update:#N` 210・`prereq:probe` 106・`state:cleanup:#N` 69・
`merge:#N` 67・`fix:#N` 49。件数そのものの削減（blocked 記録の一括化は #585、残置 worktree 容量の測定回数、
`prereq:probe` のまとめ実行）は別の対応で、本機構は「上限に達しても半端な状態を作らない」ことだけを担う。

定数 `AGENT_RUN_LIMIT` = 1000 はランタイムの上限と同じ値。`args.agentCallLimit` は「新規着手・monitoring 再開を
止める判断に使う、ランタイム上限の想定値」で、**呼び出しそのものは止めない**。開始処理・終了処理・実行中の
issue は値を超えても続行する。実行中の issue の途中で呼び出しを止めると、本機構が防ぎたい半端な状態をスクリプト
自身が作ってしまうためで、ハードキャップはランタイムが持つ。使用数が値を超えた最初の 1 回だけ警告ログを出し、
返却値 `agentBudget.reached` が `true` になる。

値は 81〜1000 の整数に限る（`args.securityReview` 有効時は 1 issue の目安が 2 増えるため下限は 83）。下限 81 = 開始処理 30 + 終了処理の予備（固定）20 + 1 issue の目安 30 + 1。開始処理
（未追跡検査・nonce・`loadState` と照合・ツリー取得・外部チェック観測・依存宣言と祖先とツリー外前提の取得・
`init-all`・孤立スキャン・残置の観測・HEAD 検査）は実測で約 20 回、依存宣言のチャンク数に比例するため余裕 10 を
足した。スクリプトハッシュの予検査（`script-hash-precheck`。`skillDir` を渡したラン〔`dryRun` を含む〕でシード取得の直後に 1 回、転記ミス・agent 例外のときだけ
もう 1 回）も開始処理に含み、この余裕 10 の内で足りる（下限 81 は変えない）。これ未満の値は 1 件も着手できないか開始処理だけで使い切るため、矛盾する入力として起動時にエラーで停止する。

開始処理の 30 は固定の見積りで、依存宣言のチャンク数（チャンクごとに 1〜数回）を式に入れていない。1,000 件規模のツリーでは
開始処理だけで 35 回前後使い、下限付近の値（例: 81）では残りが最初の 1 件に要る量（実装の目安 30 + 終了処理の予備 20 = 50）に
届かない。見積りを式にせず、**ランの終了時点**で実測して判定する（下の「予算枯渇による停滞」）。開始処理の直後（ループ前）に
着手可否を断定して `Error` で停止することはしない: monitoring 再開は予算を通っても worktree ゲートで defer され得て、
ラン中に前提が解消して ready になる安価な `verify-close` もある。いずれもループ中にしか分からず、ループ前に断定すると、
着手できたはずのランを止めたり、逆に止めるべきでないランを止めたりする。

## 予算枯渇による停滞

ランの終了時点で次をすべて満たすとき、返却値 `agentBudget.starved` を `true` にする。

- 本ランで 1 件も着手していない（`agentBudget.starts === 0`）。
- 予算で保留したノード（`agentBudgetHold` が止めた候補）が 1 件以上ある。
- そのノードの保留は予算だけが理由である（下の「終了時の note の停止理由」で成立する理由が予算だけ）。halt、新規着手抑止
  （残置 worktree 上限等のラッチ。新規着手にだけ効き、monitoring 再開は対象外）、再開ゲート（worktree の上限等）の理由が
  成立しているノードは数えない（予算以外の停止理由も記録されている）。

予算で保留したノードの note（`not-started` の note と、状態ファイルへ保存される `blocked` の note、monitoring 再開の
`interrupted` の note）は、**次ランの挙動を予測せず、保留した時点についての事実だけを書く**。次ランの必要量は、着手順・実行中の集合・
未完了ノード数・ゲート実測（`du`・`df`）に依存し、note からは決められないためである。次ランで進むこと・上限を上げれば進むこと・必要量の
下限であることを言い切る語は、予算の案内として使わない（開始時点の使用量・保留時の使用量・終了時の使用量のどれを基準にしても、別の構成で外れる）。

```text
used     = 保留時の使用量
required = 保留時に agentBudgetHold が求めた必要量（30 × 実行中 + 種別の目安 + 終了処理の予備 20。first ではない着手では chunks 項が入る）
needed   = used + required                          （N と呼ぶ。ゲートが実際に使ったしきい値そのもの。上乗せしない）
chunks   = ceil(未完了ノード数 / 100)                （保留時の観測値。first は前進保証として required からこの項を免除される）
```

保留は `remaining < required`（`limit - used < required`）のときだけ起きるので、`needed` は保留である限り常に `limit` より大きい。
「保留した時点では、`limit` が `needed` 以上なら予算検査を通った」は、同じ状態・同じ周回についての観測事実であり、次ランの予測ではない。

予算の断片は単独形（予算だけが理由）と併記形（halt・ラッチ・前提待ち・ゲートと併存）で同じ文言を使う。

> エージェント呼び出し数の予算不足で保留（保留時の使用 u/L、必要量 r。このランの着手 k 件）。保留した時点では args.agentCallLimit が N 以上なら予算検査を通った（次ランの必要量は、開始処理・先に着手するノード・ゲート実測で変わる）

- `k` は終了時の `starts`（このランの着手件数。事実）。
- `N` が指定できる上限 1000 を超えるときは、`N` の後ろに「（指定できる上限 1000 を超える）」という事実だけを添える。分割の案内は note・終了ログ・返却値に出さない:
  保留は `used + required > limit` のときにしか起きないので、既定の `agentCallLimit: 1000` では `needed >= 1001` が常に成り立つ。完了分は次ランの
  対象から外れる（状態ファイルに完了が記録される）が、それでも保留に至るランでは `needed` は 1000 を超える。分割が選択肢になり得るのは、着手 0 件（`starved`）で、
  かつ `needed` が 1000 を超える場合に限る（1 件も着手できないのに、1 件を通すのに要る量が指定できる上限を超えている）。それ以外では完了分が
  次ランの対象から外れる、という事実に基づいて判断する（これも次ランの結果の保証ではない）。
- 終了ログ（starved のとき）も同じ断片から作る。先頭は「予算不足で 1 件も着手していない。」。

返却値 `agentBudget` の関連フィールド（数値の出どころは、保留のたびに `agentBudgetHeld` へ上書きして残す保留時の記録 1 か所。note・終了ログ・
`neededLimit`・`held` はすべてこの記録の値から作る）:

- `held`: 予算で保留した全ノード（他の停止理由と併存するものも含む）を issue 番号の昇順に並べた配列。保留が無ければ、`enforced: false` のときも空配列。
  各要素は `{ issue, kind, resume, used, required, chunks, needed, budgetOnly }`。`kind` は `implement` / `verify-close`、`resume` は monitoring 再開か、
  `used`・`required`・`chunks` は保留時の値、`needed` は note に出す N と同じ値（`used + required`）、`budgetOnly` は予算だけが理由か（`stopReasons` から導く。
  note・`starved`・`neededLimit` と同じ集合）。観測値の記録であり、次ランの挙動についての主張は含まない。状態ファイルには保存しない。
  **プログラムから読むなら `held`、人が読むなら note。**
- `stoppedDispatchAt` と `held[].used` は別の時点の使用数: `stoppedDispatchAt` は**最初に**新規着手・再開を保留した時点の使用数（1 度だけ記録）、`held[].used` は**そのノードを最後に保留と判定した時点**の使用数で、ランが進むほど後者が大きくなり得る（同じ値でなくても矛盾ではない）。
- `neededLimit`: `held` のうち `budgetOnly` なものの `needed` の最小値（保留時の観測値に基づく目安）。着手の有無（`starts`）に関係なく、
  そのような行があれば値を持ち、無ければ `null`。**1000 を超え得る**（そのまま `agentCallLimit` に渡せる値とは限らない。`agentCallLimit` は
  81〜1000 の整数に限り、`securityReview` 有効時は 83〜1000）。
- `starved`: このランで 1 件も着手せず（`starts === 0`）、予算だけが理由の保留ノードがある。終了ログに警告を出す。

ここでの数値は保留時の観測であり、次ランの開始処理（状態の読み込みの再取得〔`state:load-fill`〕の回数など）や先に着手するノードの消費で必要量は変わる。
そのため note にはその旨を添えるにとどめ、予測を書かない。

## ゲートの評価と予算保留（monitoring 再開）

monitoring 再開は予算検査のあとに再開ゲート（残置 worktree の件数・バイト・実ディスク空き容量）を評価する。ゲートのうち
件数軸は算術だけだが、バイト軸（`remeasureResidualBytesNow`: `du`・必要なら孤立スキャン）と空き容量軸（`remeasureFreeDiskNow`:
`df`）は**自身がエージェントを呼ぶ**。予算が足りない周回で先にゲートを評価すると、足りない予算をさらに消費する。
そのため予算保留の周回ではゲートを評価せず、過去の周回で記録したゲートの理由（`monitoringResumeGateDeferred`）を**消さずに残す**
（#596 は消していたため、残置 worktree の defer が残るのに予算だけが理由と案内していた。Issue #598）。ゲートを通過した周回で
消え、予算を通った周回の defer で上書きされる。

終了時にゲートの理由と予算の保留が両方残る再開は「ゲートは前回観測・今回は未評価」で、note は両方を示す。このノードは
`starved` / `neededLimit` の対象に数えない（`held` には入り `budgetOnly: false`）。halt が立った場合の
組み合わせも含め、note の組み立ては次の節にまとめる。

## 終了時の note の停止理由（成立している理由をすべて並べる）

着手・再開できなかったノードの note（`not-started` の result と状態ファイルへ保存する `blocked` の note は同じ文字列、monitoring 再開の
`interrupted` の note）は、止めた理由を 1 つ選ばず、**成立している理由をすべて集めて固定の優先順に並べる**。選ぶ形（#595〜#599）は
修正のたびに 1 つの組み合わせだけを塞ぎ、未テストの組み合わせが毎回残ったため（Issue #600）。実装は `stopReasons`（理由の集合）と
`stopNote`（文言の合成）の 2 関数で、3 種類の note と `starved` / `neededLimit` の判定（`budgetOnly` = 理由が予算だけ）が同じ集合を使う。

| 順 | 理由 | 成立条件 | 断片 |
|----|------|----------|------|
| 1 | halt | `halted` が立っている（全種別） | 未着手は「halted により未着手（理由: …）」、再開は「halt のため再開しなかった（理由: …）」 |
| 2 | 新規着手抑止（ラッチ） | 再開でないノードで `shouldSkipForNewStartSuppressed` が真（空き容量起因の `implementOnly` は implement だけ） | 「残置 worktree 上限ゲートにより新規着手を抑止（理由: …）」 |
| 3 | 前提 | 前提（依存ノード）のうち `done` に無いものがある | 2 種類に分けて事実を書く（未決着 → 決着済みの順）。まだ決着していない前提（`done` にも `failedSet` にも無い）は「前提 #A が未完了のため待機」、既に `failedSet` に記録された前提（失敗・ブロック、ツリー外で open のままの前提を含む）は「前提 #B は完了していない（失敗・ブロックとして記録済み）」。多いときは「M 件（先頭 5 件: …）」。前提が未完了のノードは予算検査にもゲート評価にも届かない |
| 4 | 再開ゲート | 再開で、ゲートの defer 理由が記録されている（ゲートは implement の再開だけ） | 記録した理由。予算保留と併存するときは「この理由は前回の評価。予算で保留した周回では再評価していない」を添える |
| 5 | 予算 | 予算で保留した記録がある | 単独形・併記形とも同じ断片（上の引用）。保留した時点の使用量・必要量・しきい値 N とこのランの着手件数を事実として書く |

- 成立する理由が 1 つもないとき: 未着手は「スケジューラ終了時に未着手（キュー未到達）」、再開は「再実行すると monitor からの再開を試みる」。
  どちらも再実行の結果を言い切らない。前提が未完了のノードは理由 0 件にせず、上の「前提」として挙げる（以前は前提待ちの再開が理由 0 件の既定文になり、再開を言い切っていたが、前提が予算保留のままなら再開しない）。
- 他の理由が残るノードも、予算の断片は単独形と同じ（断片は観測の報告で、予測を含まない）。
- ゲートは予算で保留した周回では評価しない（`du`・`df` が自身でエージェントを呼ぶ）。予算保留の分岐は `agentBudgetHeld.delete` より前で `continue`
  し、ゲート評価はその後なので、「ゲートを今回再評価済み × 予算保留」は存在しない。併存するゲートは必ず前回の評価である。
- 新規着手抑止のラッチは、予算検査のあとに判定される。予算で保留したノードにもラッチは成立し得る（両方を示す）。再開ノードにはラッチは効かない。

到達できない組み合わせ（ゲート理由を持つ新規着手・verify-close の再開、再開へのラッチ、前提待ちのノードのゲート理由・予算保留）は表から外す。テスト（`tests/agent-call-budget.test.mjs`）が
上の軸 × 種別の全組み合わせを純粋関数で網羅し、代表行は stub agent のランで実際にその状態へ到達して確かめる。

## 数え方（スクリプトの `agent()` 1 回 = ランタイムのエージェント 1 件）

- 駆動部の冒頭で `agent` を、呼ぶ前に `used` を 1 増やす関数へ再束縛する。呼び出し箇所は書き換えない。
  `runStateAgent` の sonnet フォールバック、`agentRetryOnce` の再試行、fix の再起動はいずれも `agent()` を
  呼び直すので、実際に起動した数と一致する。例外・null を返した呼び出しも「起動した」ので数える。
- `pipeline()` は使わない（使うとスクリプトからは数えられない）。テストが生成物に `pipeline(` が無いことを検査する。
- 再束縛できない実行環境では数えられず、予算ゲートは効かない。その場合は返却値の `agentBudget.enforced` が
  `false` になり、ログにも出す（起動を止めずに、効いていないことを見えるようにする）。`enforced: false` のランでは
  `used` が 0 のままで判定が成り立たないため、新規着手・monitoring 再開の予算判定を適用しない（全件が従来どおり着手する）。

## 新規着手を止める式

新規着手（`monitoring` 再開と `verify-close` を含む）の前に、残り `limit - used` が次を下回れば着手しない。

```text
必要量 = 実行中の件数 × 30 + 候補の目安 + 終了処理の予備
候補の目安 = 実装 30 / monitoring 再開 12 / verify-close 6
終了処理の予備 = 20 + ceil(未完了ノード数 / 100)
```

**前進保証**: このランでまだ 1 件も着手しておらず実行中も 0 の最初の着手には、`ceil(未完了ノード数 / 100)` の項を課さない。
未完了ノードが多いと、この項だけで limit を超え、実行中 0・使用量が少ないのに全件が未着手になるため（例: `agentCallLimit: 81`・
未完了 3,101 件では必要量が 82 になる）。最初の 1 件は固定分（候補の目安 + 20）が残りに収まる限り着手し、2 件目以降は
項を課す。blocked 一括記録が想定上限を超える分は、超過の警告（呼び出しは止めない）が受け止める。

非ラッチ: 実行中の issue が終われば `running` が減り、残りが足りれば再び着手する。判定は `AGENT_CALLS_PER_ISSUE`・
`AGENT_CALLS_TERMINAL_BASE` と `agentBudgetHold`（純粋関数）に集約し、テストが式の境界を固定する。

### 1 issue の目安 30 の内訳（`AGENT_CALLS_PER_ISSUE.implement`）

通常経路の見積り（約 22）に余裕 8 を足した値。

| 段階 | 回数 |
|------|------|
| 状態書込み（開始・planning・implementing・reviewing・unverifiedPr・monitoring・終端・cleanup。フォールバックで +1 し得る） | 約 8 |
| plan・implement | 2 |
| Review 2 回 + fix 1 回（1 往復） | 3 |
| pr-create・PR 照合（`pr-bind`） | 2 |
| monitor 3 回 | 3 |
| マージ後の fix と再 monitor | 2 |
| merge-exec・merge-verify | 2 |

`args.securityReview` を有効にしたランは、Review ラウンドごとにセキュリティ専用の Review が 1 回増えるため、上の Review 2 回ぶんの 2 を足して 32 とする（`agentCallLimit` の下限も 81 から 83 に上がる）。無効なら 30 のまま。

最悪値（fix 6 回・monitor 7 回・Review 往復）は 60 を超えるが、実行中の issue は既にその一部を使っているため、
残り全量を最悪値で見積もると着手を止めすぎる。目安を超えた issue が上限へ達した場合は、下の「未監視の PR」が
受け止める。過剰に見積もったときの代償は未着手が増えること（再実行で着手し得る）で、
過小に見積もったときの代償は打ち切りなので、前者に倒している。

### 監視の待機（#603 第 2 弾）は呼び出し数を増やさない

monitor のレビュー到着待ち・required context 揃い待ち・チェック総数 0 件の再確認は、1 回の起動が壁時計 90 秒 + 数秒以内（遅い・ハングする gh を含めてスクリプトが保証する）の `observe-pr.sh --wait` を、**同じ監視エージェントが** `pending` のたびに `--attempt` を 1 増やして再実行する（最大 7 回 = およそ 10 分）。エージェント呼び出し（`agent()`）は増えず、上の「1 issue の目安」（monitor 3 回）は変わらない。

ホストが 1 回ごとにエージェントを起動し直す設計は採らなかった。待機は 1 回の監視の途中の判断（催促するか・needs-fix にするか・3e の再判定へ進むか）と地続きで、待機の前後の観測を別のエージェントへ分けると文脈の受け渡しが要る。加えて 1 つの待機が最大 7 回、1 回の監視が最大 4 か所（3e・3g・4b・4c）で待ち得るので、最悪では 1 回の監視が +28 回、監視 7 ラウンドで +196 回に及び、目安 30 と 1,000 の上限の見積りを大きく崩す。エージェント側の再実行では `agent()` が増えないので、見積りを変えずに済む。

代償は、回数の数え間違い（エージェントが `--attempt 1` を打ち続ける）をホストが止められないこと。スクリプトが保証するのは「1 回の起動が有界」と「`--attempt` の範囲検査（範囲外は exit 2）」までで、呼び出しの繰り返しそのものは止められない。エージェントが繰り返し続けても、1 回ごとが有界なので長い foreground sleep にはならないが、全体の上限はエージェント自身の遵守とホストの監視枠（`monitorsLeft`）・エージェント呼び出し予算に委ねる。

### 終了処理の予備

ループ後に走るのは `writeBlockedStateBatch`（100 件ごとに 1 エージェント。未完了ノード数から見積もる）、
孤立 worktree のスキャンと終了時の `loadState`、容量の終了時実測、スイープ、メイン worktree の未追跡検査と HEAD 検査（`worktree:head-scan`。終了時の 1 回。予算ゲートの対象ではなく無条件に実行される）で、
再測定の再試行を含めても固定分は約 20 に収まる。

## 止めたあとに返す情報

| 項目 | 内容 |
|------|------|
| ログ | 停止時点の使用量・残り・必要量。終了時に `エージェント呼び出し数: used/limit` |
| 返却値 `agentBudget` | `{ limit, used, enforced, stoppedDispatchAt, starts, starved, neededLimit, held, reached }`（`starts` は本ランで着手した件数。前進保証と `starved` の判定に使う。`starved` / `neededLimit` / `held` は上の「予算枯渇による停滞」。プログラムから読むなら `held`、人が読むなら note） |
| 未着手ノード | `notStarted` に載り、`done` の `not-started` の note が停止理由を示す。状態ファイルには `blocked` で一括記録される。note は成立している理由（halt・新規着手抑止・予算）を優先順にすべて並べる（上の「終了時の note の停止理由」）。予算の断片は保留時の観測値の報告で、他の理由があるときも同じ文言を併記する |
| monitoring 再開の見送り | `interrupted` に載り、note が停止理由を示す。halt・再開ゲート・予算の成立している理由を優先順にすべて並べる（予算でも保留した再開のゲートは前回の評価）。予算だけなら予算不足。状態ファイルの `pr` は保持される |
| 返却値 `unmonitoredPrs` | 本ランで PR 番号を得たが、実 monitor が一度も結果を返さなかった `[{ issue, pr, resumable }]`。終了ログにも出す |

`unmonitoredPrs` の PR は、番号を得た時点（照合・状態保存より前）で `resumable: false` として記録するため、その後のどこで
打ち切られても載る。照合を通り、状態ファイルへ `pr` を含む patch を書けた時点で
`resumable: true` へ上がる（`monitoring` 遷移の保存成功、またはその失敗後の `blocked` + `pr` + `branch` の退避保存の成功。
どちらも次回ランの `isActiveMonitoring` が再開対象にする条件〔status が monitoring / blocked、`pr` が正の整数、
branch がその issue の命名〕と同一で、`blockedReason` 等の追加条件は無い）。`resumable: true` は状態ファイルに `pr` が保存されており、再実行すると
monitoring 再開（Recover・Implement・PR 作成は通らない）を試みる。次ランでその再開が予算保留・ゲート defer・前提待ちになれば再開しない。`resumable: false` は再実行しても再開しないため、
返却値の PR 番号を GitHub 上で手動確認する（`unverifiedPr` が保存されていれば再実行で再照合される）。終了ログも
両者で案内を分ける。
